# 12 解释预聚合（Pre-aggregations）

> 目的：直观、有层次地说明预聚合——是什么、怎么工作、什么查询会命中、怎么查看。
> 规范依据：[docs/06-pre-aggregations.md](../06-pre-aggregations.md)（概念与参数）；
> 存储侧（数据住在哪）见 [06-解释cubestore.md](./06-解释cubestore.md)。
> 本项目实测：2026-09-23，P6 阶段（01 设计第 10 节）。

---

## 一、是什么（一句话定义）

**预聚合 = 把"按维度组合预先 GROUP BY 好的结果"物化存储，查询命中时不再扫原表。**

以本项目 `cbill`（开票）为例：每条查询都要扫 45 张月表的 UNION ALL（全项目最重
SQL）——预聚合把它的 GROUP BY 结果算好存起来，之后查询直接取现成的。

```sql
-- 预聚合物化的就是这条 SQL 的结果（存成 Cube Store 里的分区表）
SELECT state, bus_type, is_income, region_code, bill_month,
       COUNT(*) count, SUM(ftotalamt) total_amount, ...  -- 11 个度量
FROM (45 张月表 UNION ALL)
GROUP BY state, bus_type, is_income, region_code, bill_month
```

**rollup 是预聚合的类型**（默认）：把数据按"你声明的维度组合"预先分组汇总。
物化结果 = 一个"列的清单"：11 个度量列 + 5 个维度列 + 时间列 `bill_month`。

## 二、为什么需要（收益）

| 收益 | 说明 |
|---|---|
| **cbill 系 UNION 提速（本项目唯一真实受益点）** | 每条查询扫 45 张月表 → 命中后只扫几 KB 的列式分区文件 |
| **为数据增长预埋** | 千行级数据 Oracle 本来就毫秒级；数据涨到百万/亿级时不用回头改模型 |
| **验证收口（P6 的核心价值）** | 预聚合前后 diff 零差异 = 口径一致性的最终证明（见第七节） |

不做的代价：正确性零影响（口径、回归照常）——预聚合是纯增量配置。

## 三、怎么工作：一条查询的旅程

```
查询进来（cube.js query / Playground / BI）
   │
   ▼ ① 编译：查询成员 ⊆ 某个预聚合的成员清单？
   │      ├── 否 → 走 Oracle 现算（raw，external: false）
   │      └── 是 ↓
   ▼ ② 该预聚合建好了吗？
   │      ├── 没建 → 触发后台构建（首查先回 raw），建完的后续查询命中
   │      └── 建好 ↓
   ▼ ③ 走 Cube Store：在分区 parquet 上扫描/再聚合（external: true）
   │      区分实例：时间维度 = bill_month（预聚合声明的那个）才命中
   │      dateRange 边界 → 只扫范围内的分区（分区剪枝）
   ▼
结果返回（/v1/load 响应带 usedPreAggregations 命中证据）
```

### 实例：cbill 的预聚合定义（`conf/model/cubes/facts_cbill/cbill.yml` 已落盘）

流程 ① 里"成员清单"的出处——预聚合声明（rollup 类型）：

```yaml
pre_aggregations:
  - name: main
    measures:
      - CUBE.count
      - CUBE.receipt_count
      - CUBE.total_amount
      - CUBE.avg_amount
      - CUBE.normal_count
      - CUBE.void_count
      - CUBE.income_amt
      - CUBE.regular_amt
      - CUBE.ebill_paper_amt
      - CUBE.offset_amt
      - CUBE.direct_transfer_amt
    dimensions:
      - CUBE.state
      - CUBE.bus_type
      - CUBE.is_income
      - CUBE.region_code
      - bill_type.name
    time_dimension: CUBE.bill_month
    granularity: month
    partition_granularity: month
```

- **measures + dimensions** = "成员清单"（第四节"成员 ⊆ rollup"的判定依据）
- **time_dimension + granularity: month** = 物化"按月分组"的汇总结果
- **partition_granularity: month** = 44 个月 = 44 个物理分区（与 UNE_CBILL 物理
  分表对齐，查某月只扫该分区）

**三个关键行为**（实测）：
1. **异步构建**：首次查询触发后台构建，首查先回 raw 数据——`usedPreAggregations`
   缺失是"构建未完成"不是"不命中"
2. **构建耗时**：44 分区 × 2 cube 逐月构建约 10 分钟；无时间过滤的查询需全部分区建完
3. **自动刷新**：scheduled_refresh 默认开启——源数据变化（refresh_key 变）→
   受影响分区自动重建（P6 实测：重建了 88 个分区）

## 四、命中规则：成员 ⊆ rollup（三层）

预聚合的成员清单 = **物理上存在的列的集合**。查询要的每一列都在清单里，Cube Store
才有能力只用自己的数据回答——缺任何一列就回 Oracle。

| 层 | 规则 | 实例 |
|---|---|---|
| **1. 列必须物理存在** | 查询的 measures/dimensions 都在 rollup 定义里 | 查 `bill_date` 不命中（rollup 的时间列是 `bill_month`） |
| **2. 子集命中（rollup 名字的由来）** | 存的是最细粒度，查询用更少维度 = 在已存行上**再聚合一次**（向上卷起） | 存了 state×bus_type×…×bill_month，查 `count by state` = 再 GROUP BY 一次 → 命中。再聚合只对加和型 measure 成立——**countDistinct 不能从分组结果再聚合** |
| **3. filter member 也要在** | filter 变成对预聚合列的 WHERE，列不在就没法过滤 | `cbill.bill_no 过滤单票` 不命中（明细 rollup 没有主表维度） |

## 五、命中示例（12 条，全部实测）

> 判读：每条命令末尾自报——`[预聚合命中] dev_pre_aggregations.cbill_main（extDbType: cubestore...）`
> = 走 Cube Store；`[未命中预聚合] 走源库（Oracle）查询` = 走 Oracle。

**应命中（7 个）：**

```bash
# 1. 纯度量（无维度、无时间）——rollup 成员子集
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.normal_count\",\"cbill.void_count\"]}'"
# 2. 按状态分组（无时间过滤）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.count\"],\"dimensions\":[\"cbill.state\"]}'"
# 3. 按月分布（时间维度 = 预聚合的 time_dimension）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.receipt_count\"],\"timeDimensions\":[{\"dimension\":\"cbill.bill_month\",\"granularity\":\"month\"}]}'"
# 4. 按月 + 按状态组合（维度切分自由组合）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.total_amount\"],\"dimensions\":[\"cbill.state\"],\"timeDimensions\":[{\"dimension\":\"cbill.bill_month\",\"granularity\":\"month\"}],\"limit\":5}'"
# 5. dateRange 时间边界（构建完成后命中，只扫相关分区）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.count\"],\"timeDimensions\":[{\"dimension\":\"cbill.bill_month\",\"dateRange\":[\"2026-09-01\",\"2026-09-30\"]}]}'"
# 6. region_code 维度（JWT 行级过滤的同款维度）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.count\"],\"dimensions\":[\"cbill.region_code\"],\"limit\":3}'"
# 7. cbill_item 按项目名（明细 rollup）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill_item.count\",\"cbill_item.total_amount\"],\"dimensions\":[\"cbill_item.item_name\"],\"limit\":3}'"
```

**应不命中（5 个对照）：**

```bash
# 8. 按开票日期（bill_date 不在 rollup，时间列是 bill_month）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.total_amount\"],\"timeDimensions\":[{\"dimension\":\"cbill.bill_date\",\"granularity\":\"month\"}],\"limit\":3}'"
# 9. YTD（rolling window 宏度量，不进 rollup）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.amt_year_to_date\"],\"timeDimensions\":[{\"dimension\":\"cbill.bill_date\",\"dateRange\":[\"2026-01-01\",\"2026-12-31\"]}]}'"
# 10. 按票种（join 维度实测不命中——countDistinct × join 维度约束）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.receipt_count\"],\"dimensions\":[\"bill_type.name\"],\"limit\":3}'"
# 11. 单票下钻（cbill.bill_no 主表维度不在明细 rollup）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill_item.count\"],\"dimensions\":[\"cbill_item.item_name\"],\"filters\":[{\"member\":\"cbill.bill_no\",\"operator\":\"equals\",\"values\":[\"0000000003\"]}]}'"
# 12. 脱敏列（payer_name 不在 rollup，且数据是脱敏值，属预期不命中）
docker exec cube sh -c "node /cube/agent/cube.js query '{\"measures\":[\"cbill.count\"],\"dimensions\":[\"cbill.payer_name\"],\"limit\":3}'"
```

**规律总结：**

| 规律 | 说明 |
|---|---|
| 成员 ⊆ rollup | measures/dimensions（含 filter member）全在定义里 → 命中 |
| 时间维度必须匹配 | `bill_month` → 命中；`bill_date` → 不命中 |
| 时间过滤可选 | 无过滤 / granularity / dateRange 都命中（**构建完成后**） |
| join 维度例外 | `bill_type.name` 在定义里但实测不命中（countDistinct × join 维度约束，raw 兜底正确） |

## 六、怎么查看命中（三条路，全部实测）

| 路 | 命令/位置 | 输出 |
|---|---|---|
| **CLI 自报** | `cube.js query '...'`（每次查询自动带） | `[预聚合命中] dev_pre_aggregations.cbill_main（extDbType: cubestore，external: true）` |
| **编译计划** | `cube.js sql '...'`（只编译不执行） | `external: true` + `FROM dev_pre_aggregations.cbill_main`；未命中则 `external: false` + FROM 原表 UNION |
| **Playground** | 查询构建器底部 **PreAggregationStatus 组件**（bundle 实扫验证） | 命中："Query was accelerated with pre-aggregation"；未命中：link 按钮一键进 Rollup Designer |

**命中证据字段勘误**：`/v1/load` 响应的命中字段是 **`usedPreAggregations`**
（不是 `preAggregations`——01 设计原写法实测不回显）。

## 七、本项目实测配置（P6 已落盘）

| cube | rollup 配置 | 成员选择依据 |
|---|---|---|
| `cbill` | `time_dimension: bill_month`，`granularity: month`，`partition_granularity: month` | 11 measures + 5 dimensions（含 `region_code`——JWT 行级过滤在该维度上，不含则 JWT 查询永不命中），按 `regress/cbill.queries.json` 12 条回归用例反推 |
| `cbill_item` | 同上 | 4 measures + 4 dimensions |

两个关键取舍：
- **`amt_year_to_date`（rolling window 宏度量）不进 rollup**：窗口度量需全量
  时间范围物化，YTD 查询走 raw（dateRange 有界，代价可接受）
- **paybook/stock/suspicious/writeoff 系暂缓**：千行级 latency 收益有限，"按需"再补

## 八、P6 实测收获（验证收口）

**1. 数据漂移发现（预聚合忠实性的最强证明）**——diff 回归首跑发现基线不一致，
三重证据定位为**源数据漂移而非预聚合缺陷**：
- 预聚合 state 1 = 31602，P3 基线 31591（+11）；state 2 = 726 不变
- `db.js` 直查真相：月表合计 **32328** = 预聚合合计——预聚合与源数据完全一致
- diff 全部 delta 精确 = +11 / +11.00，漂移全部落在 2026-09（P3 后新增 11 笔正常票据）

**2. 口径一致性证明链**：db.js 直查真相（32328）= 预聚合结果（32328）=
diff 基线更新后回归零差异——预聚合忠实服务当前源数据。

**3. 回归结论**：cbill/views/paybook 基线 re-snap（漂移更新）后零差异；
writeoff/bill_kpi 首跑即通过；stock 的 queries 文件已从 baseline 反推恢复
（12 条用例）并 re-snap——**六组基线全部回归通过**；paybook 的
`expired_count` 是 SYSDATE 度量（feffdate < today）逐日漂移，属设计内预期行为。

**4. 暂缓项**：其他 cube 的 plain rollup（按需）、按票种 join 维度不命中的
原因深查（raw 兜底正确，不阻塞）。

---

**一句话总结**：预聚合 = 预先算好的 GROUP BY 结果（rollup 定义了列的清单）；
查询成员 ⊆ 清单就命中 Cube Store 现成数据，缺一列就回 Oracle 现算——
收益在 45 表 UNION 的物化，价值在 diff 零差异的口径一致性证明。
