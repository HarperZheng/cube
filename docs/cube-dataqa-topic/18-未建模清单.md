# 18 未建模清单（每个事实 cube 的源列盘点）

> 状态：**设计定稿（2026-09-27 两轮拍板）**——第一轮：五类分类学＋每类触发语义；
> 第二轮：**存储工程化——独立 JSON（`conf/unmodel/<cube>.json`）＋校验工具
> `agent/ledger.js`，yml 零接触**（首版"yml 头注释"方案随之废弃：注释是文档，
> 工程方案把清单升级为**受测工件**，对齐项目 snap/diff 哲学——不信任手维护，用工具验证）。
> 其余未决项见 §6 待定事项。
> 定位：16 号文档 §7 #1 的实施载体。FSUB\* 事故（16 号 §3.4）的根因之四是
> "无列账本：56 列建 26、剩 30 列无声缺席——'没建模'与'没看见'不可区分"；
> 本清单把缺席变成**已盘点、每列有交代**。
> 命名注记：16 号 §7 #1 原称"未建模列账本"，2026-09-27 定名**未建模清单**。

## 0. 收益：一次 15 分钟/cube 的盘点，换什么

| 面 | 没有清单（现状） | 有清单 |
|---|---|---|
| **问数撞缺口（失败模式 d）** | 答不了"源表到底有没有这列"——要确认就得转 modeling 开流程核查源表，分钟到天级 | 一条命令即知（`ledger.js show`）："业务未需求：FOWNIMAMT（本级金额）"——源表有料、可补建。话术从"我不确定，要核查"变成带证据的"支持，补建约几分钟" |
| **FSUB\* 式事故（16 号全案）** | 真业务列静默缺席 → agent 答"查不了" → 用户拍板绕路（双口径 workaround、跨事实表拆分）→ 事后排查才发现源表自带列，再返工 | daybook 的 12 列业务未需求列（资金性质/主管部门/预算单位/直缴汇缴/本级金额……）全部有交底——同类事故从根上堵住 |
| **建模原料核实（分支② / ③-1）** | 每次补建都 user_tab_columns 全列重扫、逐列读注释定性 | 分类结论直接复用；"（待核实）"标注＝提前挂号的调查任务 |
| **接手/审计** | 30 列缺席是黑洞，"没建模"与"没看见"不可区分 | 每列有交代、可审计；新人/新 agent 查一册 JSON 即得全貌 |
| **过期防护（工程方案独有）** | — | `check` 硬门：源表加列、在册列被补建、totals 漂移 → 当场报警（注释方案无此能力） |
| **成本** | — | 一次性 15 分钟/cube（§7 流程），独立 JSON 零编译风险、Cube 升级零关联（§2） |

一句话：**把"没建模"与"没看见"变成可区分**——问数答得更准、补建走得更快、缺席有交代。

## 1. 是什么 / 不是什么

**是**：每个事实 cube 一册的「源列 → 建/未建/原因」**机器可读登记**——JSON 存储、
schema 约束（类别枚举）、工具校验（survey / check / show，§4）。

**不是**：

- **不在 yml 里**——独立于 `conf/model/`，Cube 编译器 / schema 校验 / 官方升级全程零关联
  （2026-09-27 拍板：不修改 yml 格式定义，注释方案也一并废弃）
- **不复制已建列**——已建列的唯一真相是 yml 成员的 sql 引用，`check` 每次现场重算比对；
  清单里的 `totals` 只是**断言**，不是第二份维护点
- **不是纯文档**——`check` 退出码 0/1，可进 modeling 交付步骤与将来 CI，过期即报警

## 2. 存储结构（拍板：`conf/unmodel/<cube>.json`）

**目录名 `unmodel` = 未建模（un-modeled）**，与 `conf/model/` 平级成对照：
`model/` 放已建的，`unmodel/` 登记未建的。每事实 cube 一册：

```
conf/
  model/          # Cube 扫描（schemaPath），已建模型——清单不碰这里
  unmodel/        # Cube 不扫描（不在 schemaPath 下，且 Cube 只认 schemaPath 内 yml/js）
    daybook.json
    treasury_item.json
    ...
```

容器可达性（零 compose 改动）：compose 挂载是整目录 `- ./conf:/cube/conf`，
`conf/unmodel/` 自动出现在容器内 `/cube/conf/unmodel/`——容器内 `ledger.js` 直接读写。

JSON 结构（daybook 缩略示例，完整首例见 §8）：

```json
{
  "schema": "unmodeled-inventory/1",
  "cube": "daybook",
  "source_table": "FNE_INCOME_DAYBOOK",
  "surveyed_at": "2026-09-27",
  "totals": {"source": 56, "built": 26, "unmodeled": 30},
  "trigger_semantics": {
    "technical": "系统流程/预留字段——不主动建；口径排查发现依赖时再评估",
    "id_key": "识别码，编码/名称已建或走 join——查询成员永不建；join 在声明里用",
    "redundant_snapshot": "快照与 join 二选一落败者——口径争议时重评 join vs 快照",
    "business_unneeded": "真业务语义、暂无消费场景——问到即 cube-modeling 分支②补建",
    "detail_trace": "单据级流水码——明细下钻场景出现时建（进明细粒度）"
  },
  "entries": [
    {"column": "FOWNIMAMT", "comment": "项目收入金额(本级)", "category": "business_unneeded"},
    {"column": "FSUBID", "comment": "收入科目Id", "category": "redundant_snapshot",
     "note": "快照列族孤悬 ID（FSUBCODE/FSUBNAME 已建）；join 方案已评估弃用"},
    {"column": "FIMAGENIDCODE", "comment": "收入单位识别码", "category": "id_key",
     "note": "join 键已用未作成员"}
  ]
}
```

设计要点：

- **entries 扁平、一列一行**——git diff 里每列独立成行，补建划掉、新增入册原子可见
- **只存未建列**（差集）；`totals` 三数都是断言，由 `check` 对现场重算值验证
- **类别是枚举**（§3 五类，键名待定项见 §6）；`trigger_semantics` 进结构——每册自包含，
  读清单的人（agent 或人）不需要翻本文档就知道行动指引
- 维护规则：分支②补建某列后跑 `survey`（自动把已建列提出待删、更新 totals）；
  源表将来加列 → `check` 报 drift 逼补盘点

## 3. 五类分类学（判据 + 触发语义，2026-09-27 拍板）

设计原则：**类别名 = 不建的原因；每类背后挂一个"什么情况下会建"的触发语义**。
翻清单的人（agent 或人）扫一眼类别就知道这列值不值得抱期望、该走哪条路。

| 类（枚举键，待 §6 定稿） | 判据（为什么不建） | 触发语义（什么情况下会建） |
|---|---|---|
| **技术列** `technical` | 系统流程/预留字段：版本、变更标志、生成标志、批次号、FCUSTOM\* 自定义扩展空列——无业务语义 | 几乎永不建；口径排查发现暗中依赖它时再评估 |
| **ID/内部键** `id_key` | 识别码/代理键；对应编码/名称列已建或走字典 join | 作为**查询成员**永不建；join 需要时在 join 声明里用 |
| **冗余快照** `redundant_snapshot` | 源表自带的字典字段快照，与 join 方案二选一后的落败部分 | 口径争议时**重新评估** join vs 快照（daybook sub_name 即翻案先例） |
| **业务未需求** `business_unneeded` | **真业务语义**，只是暂时没人问 | **问到即 cube-modeling 分支②补建**——FSUB\* 事故的原生类别，清单价值的最大来源 |
| **明细追踪** `detail_trace` | 单据级流水码/缴款码，高基数，只服务明细定位不做分组聚合 | 明细下钻场景出现时建（大概率进明细粒度 cube 而非分组维度） |

三条边界规则（归类拿不准时用）：

1. **FCUSTOM\* 自定义扩展空列** → 技术列，批量一行带过（"系统预留空列"）
2. **语义不明/列注释自相矛盾** → 暂归业务未需求并标注待核实（标注机制待定，§6）；
   核实后改类或补建——让"不知道"诚实可见，不硬塞
3. **冗余快照 vs ID 键**：快照列族的其他成员已建、剩它孤悬（如 FSUBID）→ 冗余快照；
   从来没有对应建过任何成员 → ID/内部键

## 4. 工具：`agent/ledger.js`（survey / check / show）

第三个工具层脚本（与 cube.js / db.js 平级），随既有挂载 `- ./agent:/cube/agent`
自动进容器，零 compose 改动。形态待定（独立文件 vs db.js 子命令，§6）。

```bash
# 盘点（半自动）：Oracle user_tab_columns + 解析 yml 成员 sql 引用 → 算差集 → 生成/更新骨架
#   新出现的源列挂"待核实"；已建列自动提出待删；人工分类过的条目保留不动
docker exec cube sh -c "node /cube/agent/ledger.js survey daybook"

# 校验（硬门，退出码 0/1）：现场重算事实 vs 清单断言，全部通过才绿
docker exec cube sh -c "node /cube/agent/ledger.js check daybook"

# 消费（人/agent 查询）：可按类别过滤
docker exec cube sh -c "node /cube/agent/ledger.js show daybook --category business_unneeded"
```

`check` 检查项（把"希望它不过期"变成"过期就报警"——注释方案给不了的能力）：

- 源列总数：清单 `totals.source` == Oracle user_tab_columns 实数
- 已建列数：`totals.built` == yml 成员 sql 引用的去重列数（join 条件里的列**不算**已建）
- 覆盖完备：每个源列要么已建、要么在 `entries` 里，不许有黑洞
- 无陈旧条目：在册列不得已被建成成员（建了忘删册子 → 报）
- 枚举合法：category ∈ 五类；`totals.unmodeled` == entries 条数

集成点：modeling 分支②交付步骤（与 diff 回归并列跑 `check`）；分支③-5 新 cube 交付
同步产出首册；将来可挂 CI。

## 7. 制作流程（单个 cube 约 15 分钟）

1. **survey**：`ledger.js survey <cube>`——自动算差集（源列 − yml 成员列引用，
   join 条件列不算已建）、生成骨架，新列挂"待核实"
2. **人工归类**：列注释为主要依据，按 §3 判据＋边界规则逐条填 category/note
3. **落盘**：`conf/unmodel/<cube>.json`
4. **check 跑绿**：`ledger.js check <cube>` 退出码 0 才算成册
