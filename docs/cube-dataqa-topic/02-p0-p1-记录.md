和 AI 上下文一个"看目录就知道文件角色"的约定。

## 2. P0 动态数据模型链路

### 2.1 为什么 globals.py 必须在 conf/model 根（不能挪去 patch/）

这是 **Cube 服务端硬约束**，不是偏好：

- `@cubejs-backend/schema-compiler/dist/src/compiler/DataSchemaCompiler.js:139`：
  `files.find(f => f.fileName === 'globals.py')` —— 按**文件名**（不含路径）
  从 `repository.dataSchemaFiles()`（即 schema 根 conf/model 递归清单）里查找。
- 结论：`globals.py` 放 conf/model 下任何子目录都能被找到，但**改名或改扩展名
  一定找不到**；约定俗成放 schema 根（官方文档 model/jinja 章节同款路径）。
- 曾评估过 `conf/patch/globals_impl.py`（实现体）+ 根部 shim（`from ..patch...`
  不可能，schema 编译器 exec 单文件、无包结构）等拆分方案，全部不成立。
  **最终决策：完整实现直接写在 conf/model/globals.py，不拆分。**

代价与接受理由：globals.py 会被 exec（无 \_\_pycache\_\_），且出现在
localhost:4000 的 data model 界面文件列表里。它含数据源连接逻辑但**不含明文
密钥**（全部从环境变量读取），dev 模式下该目录本就对可达者可读，风险可接受。

### 2.2 为什么 Dockerfile 加 python 依赖层

- 官方 cubejs/cube 镜像内置 python3.13（@cubejs-backend/native 的 PyO3 扩展），
  **但没有 pip**（无 ensurepip），所以补依赖必须走 get-pip.py：

  ```dockerfile
  RUN wget -qO /tmp/get-pip.py https://bootstrap.pypa.io/get-pip.py \
   && python3 /tmp/get-pip.py --break-system-packages \
   && pip3 install --break-system-packages --no-cache-dir oracledb \
   && rm -f /tmp/get-pip.py
  ```

- **不能 `pip install cube`**：PyPI 的 `cube` 是无关包，会**遮蔽**内置的原生
  `cube` 模块（`from cube import TemplateContext` 会报 `from api import *`）。
  内置模块由 @cubejs-backend/native 提供，无需安装。
- requirements.txt 声明 oracledb 仅作文档性记录；实际安装只发生在镜像层
  （构建时固化，容器重建不丢）。

### 2.3 preload.js 为什么保持根目录

- 它是 **Cube 启动期钩子**（CUBEJS_WEB_SOCKETS 之外 cube 核心在启动时 require
  容器 /preload.js），挂载方式 `./preload.js:/preload.js` 已在 docker-compose.yml
  里存在——**保持原位即可生效，挪动反而要动 docker-compose.yml（违反零修改）**。
- 职责（均为 11g 服务端兼容补丁，只加不改源码）：
  1. 启动即初始化 oracledb thick 模式（11g thin 不支持，见 §2.6）；
  2. 11g 不支持 `FETCH FIRST`，改写 `FETCH NEXT n ROWS ONLY` 分页为 ROWNUM；
  3. 快速 tablesSchema（绕过慢的 Oracle 元数据查询）。

### 2.4 docker-compose.yml 零修改原则（用户约束）

- compose 是既有工程的安全边界：网络 192.168.220.0/24（避开公司内网
  172.18.0.0/16 冲突）、挂载关系、环境变量注入均已定型。
- 所有新增能力都通过**已存在的挂载点**落地：
  - `./conf:/cube/conf` → globals.py、dims/、facts_cbill/ 全部进 conf；
  - `./preload.js:/preload.js` → 11g 补丁保持根目录；
  - 依赖进 Dockerfile 镜像层（构建期，不改运行时挂载）。
- 曾被要求恢复过一次（改挂载的尝试被否决），现为原样零修改状态。

### 2.5 facts_cbill/ 子目录与 cbill_item.yml 为什么单独建

- `cbill_item` 是**事实 cube**（业务流水、度量丰富），与 P1 的维度 cube 角色
  不同，所以不进 dims/，独立放 `cubes/facts_cbill/`（按主题分组：facts_cbill
  = 用票主题；后续 P2 计划 facts_paybook、P4 facts_stock 同理）。
- 它单独建文件的直接原因：它是**方案 B（动态数据模型）的载体**——
  按月分表 `UNE_CBILL_ITEM_YYYYMM`（实测 55 张，其中 42 张有效月份
  2023-02~2026-09），表名集合在**编译期**由 globals.py 的
  `cbill_item_tables()` 枚举，新月份建表后模型零维护。
- 当前 SQL（关键片段）：

  ```yaml
  sql: |
    {%- set tables = cbill_item_tables() %}
    {%- for t in tables %}
    {%- set ym = t[-6:] %}
    SELECT {{ t | safe }}.*,
           TO_DATE('{{ (ym[:4] ~ '-' ~ ym[4:] ~ '-01') | safe }}', 'YYYY-MM-DD') AS "BILL_MONTH"
    FROM {{ t | safe }}
    {%- if not loop.last %} UNION ALL {% endif %}
    {%- endfor %}
  ```

- 命名勘误：源表注释"电脑票"是源系统对财政电子票据开具的内部叫法，
  cube 面向消费方用业务语言——title 定为 **开票明细**，"电脑票"不出现在
  title/描述中（用户指出"电脑票明细"不合理后修正，并记录命名原则）。

### 2.6 P0 特殊代码逐条解释

| 代码 | 作用 | 踩坑记录 |
|---|---|---|
| `oracledb.init_oracle_client(lib_dir='/opt/oracle-client')` | 初始化 thick 模式 | Oracle 11g 服务端，thin 模式仅支持 12.1+；python-oracledb 26.x 已改 snake_case（旧 `initOracleClient` 报 AttributeError）；捕获 'already initialized' 避免与 preload.js 二次初始化冲突 |
| `conn.cursor()` + `cur.execute()` + `cur.close()` | 执行查询 | python-oracledb 26.x **移除了 `Connection.execute`**，必须经游标 |
| `{{ t \| safe }}` | Jinja 插值进 SQL 必须加 safe | 默认转义把表名渲染成 JSON 引号形式，`{{ ym[:4] }}` 漏 safe 时渲染为 `"2023"`，拼进 TO_DATE 报 ORA-01841 |
| `t[-6:]` + `ym[:4] ~ '-' ~ ym[4:] ~ '-01'` | 从分表名提取月份构造月初日期 | BILL_MONTH 时间维度来自物理分表名，查询按月分组免于对 FDATE 取月 |
| `{CUBE}."FID"` 全大写带引号 | Oracle 标识符 | 建表用引号建的大写列名，SQL 里必须带引号精确匹配 |
| `TO_DATE({CUBE}."FDATE", 'YYYY-MM-DD')` | VARCHAR2 日期列转 time | 源表日期存字符串，不转则无法做时间粒度/过滤 |

## 3. P1 维度层

### 3.1 为什么有 dims 目录（重点）

**语义层的基本分工**：事实 cube（流水、度量、大表）与维度 cube（主数据、
描述属性、被引用）在建模方式、维护节奏、消费方式上都不同。把维度 cube 收拢
到 `cubes/dims/` 一表一文件，收益是：

1. **角色可推断**：看目录即知"这是被 join 引用的主数据"，不必逐文件读 SQL 判断；
2. **变更频率隔离**：主数据（区划/单位/票种/科目/项目）变更极慢，事实模型
   频繁迭代时不会误碰维度文件；
3. **对应设计文档 §4**：设计时就是按"5 个维度 cube"一组规划的，目录与
   设计清单一一对应；
4. **AI/消费方友好**：view 层（P5）引用维度时，按目录检索即可枚举可用维度集。

同时明确边界：**目录不影响编译**——Cube 平铺加载，dims/ 里的 cube 与
cubes/ 根下的 cube 在 schema 里完全平权。区别只在人的约定。

### 3.2 什么内容做 dims 的子 yml（判断标准）

一个源表进入 `dims/` 需同时满足：

| # | 标准 | 反例（不进 dims/） |
|---|---|---|
| 1 | 源是**描述性主数据/码表**（回答"谁、什么、哪里"） | UNE_CBILL_ITEM_*（业务流水 → facts_cbill/） |
| 2 | 被（或将被）**多个事实 cube join 复用** | 只被单一指标使用的临时中间表 |
| 3 | 度量只有 `count`（行数统计），**无 sum 类业务度量** | 事实表（金额/数量 sum） |
| 4 | `public: false`——**只通过 join 被事实 cube 引用**，不直接对外暴露 | 需要独立出报表的宽表 |
| 5 | 一表一文件，文件名 = cube 名 | 多个小码表合挤一个 yml（维护困难） |

P1 实际入 dims/ 的 5 个：

| 文件 | 源表 | 行数 | 角色 |
|---|---|---|---|
| region.yml | AFA_AUTH_REGION | 191 | 区划（事实表按 FRGNCODE→FCODE 关联，已验证 FCODE 全表唯一） |
| agency.yml | FAB_AGEN | FISFINAL=1 → 336 | 单位（版本链，取最新版） |
| bill_type.yml | FAB_BILL | 93 | 票种（事实表按 FBILLID→FID 关联） |
| item.yml | FAB_ITEM | FISFINAL=1 → 1431 | 收费项目（版本链 + 识别码复用毛刺，见 §3.3） |
| subject.yml | FAB_SUBJECT | 3711 | 收费科目（按年度存储 2020-2026） |

不进 dims/ 的既有模型：`cubes/bill_kpi.yml`、`cubes/fab_bill.yml` 是前一期
迁移产物，不在本次维度体系内，留待 P5 视图层时统一决定去留。

### 3.3 五个维度 cube 的建模决策（逐文件）

#### region.yml —— 最标准的维度 cube

- `sql_table: AFA_AUTH_REGION` 直连，无加工；
- 数据核实：**FCODE 191=191 全表唯一**，事实表按 FRGNCODE 关联此列安全
  （这是做 join 前的必做验证，写进文件头注释）；
- `id`（ID）为主键但 `public: false`——技术主键不对外，对外关联键是 code；
- level（树级次）与 bgt_level（预算级次）语义易混，description 与 meta.ai_context
  双处说明。

#### agency.yml —— 维度加工放在 sql_table 内

- 版本链：FAB_AGEN 同码多行，**FISFINAL=1 恰好全唯一**（不过滤会行倍增），
  过滤写进 sql_table 子查询；
- 行业名称翻译（字典 117）也嵌在 sql_table 里做 LEFT JOIN，而不是 cube 层 join：

  ```yaml
  sql_table: >
    (
      SELECT a.*, d."FNAME" AS "INDUSTRY_NAME"
      FROM FAB_AGEN a
      LEFT JOIN AFA_RES_DICTITEM d
        ON d."FCODE" = a."FINDCODE" AND d."FDICTCODE" = '117'
      WHERE a."FISFINAL" = 1
    )
  ```

  原则：**取数加工（去版本、翻译码值）在 sql_table 做，语义关联（事实↔维度）
  在 joins 做**——sql_table 保持"一行的物理含义不变"（仍是"一个单位"），
  cube 层 join 才不会改变粒度。
- 主动声明 `joins: region`（many_to_one，`FRGNID = region.ID`），使传递 join
  生效：事实 cube 只需 join agency，即可透过 agency 查 region 属性
  （实测 `agency.count by region.name`：云南省本级 316）。

#### item.yml —— 组合键处理数据毛刺

- 版本链同 agency：FISFINAL=1 取最新（1556→1431）；
- **实测发现 3 个 FITEMIDCODE 被两个不同项目复用**（如 530020000027 同时是
  "国家开放大学收费"与"捐赠专用"）——单独用识别码 join 会错配；
- 处理：拼接维度作组合主键，已验证 (FITEMIDCODE, FITEMCODE) 全表唯一
  1431=1431：

  ```yaml
  - name: item_key
    sql: "{CUBE}.\"FITEMIDCODE\" || '-' || {CUBE}.\"FITEMCODE\""
    primary_key: true
    public: false
  ```

- P3 建 cbill_item↔item join 时按组合键关联（事实表自带 FITEMCODE，
  202601 实测 155 行 100% 匹配且 FITEMCODE 完全一致）；
- meta.ai_context 明确警告识别码复用问题，供 AI 查询时规避。

#### subject.yml —— 按年度存储的维度

- 源表按年度存 2020-2026 共 3711 行，`year` 作为普通 number 维度暴露，
  查询时按年度过滤取对应版本；
- 与 item 的关联关系**未核实**（FAB_ITEM 未直接含科目编码），**暂不声明
  join**——宁可少声明一个错误的 join，也不猜（文件头注释记录待办）。

#### bill_type.yml —— 最薄的码表维度

- `sql_table: FAB_BILL` 直连，id 主键即事实表 FBILLID 关联键；
- 仅有的加工是两个 `TO_DATE`（FEFFDATE/FEXPDATE 为 VARCHAR2 'YYYY-MM-DD'），
  使生效/失效区间可做时间过滤；
- 票据性质/开票方式仍是代码值，字典翻译留待后续接入（注释记录）。

### 3.4 P1 实测中的错误与修正

| 错误 | 原因 | 修正 |
|---|---|---|
| `(value = [object Object]) must contain at least one of [sql, sqlTable]` | region/bill_type/subject 初版漏写 sql_table | cube 定义必须含 sql 或 sqlTable 之一，直连表也要写 `sql_table:` |
| 传递 join 不生效风险 | 维度间关系未显式声明 | agency 主动声明 join region（many_to_one），实测传递 join 正常 |
| 同码行倍增风险（agency） | 版本链未过滤 | FISFINAL=1 写进 sql_table，实测 336=336 唯一 |
| 识别码错配风险（item） | 3 个 FITEMIDCODE 被复用 | 组合键 (FITEMIDCODE, FITEMCODE) 去重，join 按组合键 |

### 3.5 P1 验证结论（agent/cube.js 实测）

- `/v1/meta` 含全部 5 个维度 cube，编译零错误；
- 各 count 度量：region 191 / agency 336 / bill_type 93 / item 1431 / subject 按年分布正确；
- 传递 join：`agency.count by region.name` → 云南省本级 316、昆明市本级 13；
- 容器纯净性复核：`/cube/node_modules` 0 modified 文件，oracledb 来自镜像层。

## 4. 沉淀给后续阶段的约定

1. **新事实 cube 一律进 `cubes/facts_<主题>/`**（P2 facts_paybook、P3 复用
   facts_cbill、P4 facts_mgmt），维度一律进 `cubes/dims/`；
2. **join 前必验证关联键唯一性**，验证结论写进文件头注释（含行数证据）；
3. **取数加工在 sql_table、语义关联在 joins**，sql_table 不改变行粒度；
4. **有版本链的源表必须过滤 FISFINAL=1** 并验证过滤后唯一；
5. **Jinja 插值进 SQL 必加 safe**；VARCHAR2 日期列必须 TO_DATE 转 time；
6. 不确定的关系**宁可不声明 join**，记录在文件头待办区（subject↔item 模式）；
7. **多表同口径用 `extends` 复用成员定义**，不复制粘贴 measures；时间口径度量
   （to_date 系列等"一个度量 × N 周期"形状）用 **Jinja 宏批量生成**（P3 实测
   通过：`model/macros/` + `{% import %}`，详见 04 记录 §5；宏在编译期生成
   度量，省掉的是源码重复，不减少成员数）；
8. **行级权限用 access_policy 双互补策略**（P2 最终方案，详见 03 记录）：
   有属性走 `row_level` 过滤、无属性走 `conditions: not securityContext.X` +
   `row_level: allow_all` 显式放行。**硬语义：策略存在 = 白名单制，未命中
   任何策略的用户被整表拒绝（1=0）**——每种用户状态必须至少命中一条策略。
   单策略 + conditions（缺失回落默认全行）在 Core 中不存在；query_rewrite
   是可行中间方案（曾落 conf/cube.py，container.js:178 自动检测 cwd，后随
   切回声明式删除），仅当声明式表达不了时才用。签测试 JWT 用
   `agent/cube.js secret` 取最新（**apiSecret 每次重启重新生成**，旧 secret
   签的 token 静默不过滤）；
9. **含 SYSDATE 的度量过滤器不参与预聚合命中**（预聚合按固定过滤值匹配），
   measure description 写明，P6 回归时不误判为预聚合缺陷；
10. **view `includes: "*"` 必须显式 excludes 技术主键**——included 成员不
    继承 cube 的 `public: false`（docs/07），fid/item_key/agency.id 等逐一排除；
11. **view 的 join_path 必须显式钉死多路径**（docs/05：多路径结果不可预测，
    如 paybook→region 直达 vs 经 agency 传递）；
12. **口径回归每阶段收尾即 snap**（P2 起 `regress/<主题>.baseline.json` 落盘），
    P6 只做全量 diff + 预聚合前后对比，不临时补建基线；
13. **joins 的 sql 引用物理列，不引用维度名**（P2 踩坑：`{region}."CODE"`
    报 ORA-00904 invalid identifier——join SQL 中 `{other}.col` 是把物理表
    别名替换进去，col 必须是物理列，如 `{region}."FCODE"`）；
14. **REST API 查询字段是驼峰 `timeDimensions`**（snake_case 报
    "time_dimensions is not allowed"），filters/values 同理；
15. **动态 UNION 不用 `SELECT t.*`，按列交集显式展开**（P3 踩坑：不同月份建的
    表列集不同——cbill 月表 104/105/106 列不齐，`SELECT t.*` 的 UNION 报
    ORA-01789；globals.py 的 `monthly_columns(prefix)` 返回有效月表列交集）；
16. **成员名控制在"cube 前缀 + 成员名 ≤ 30 字符"**（P3 踩坑：Oracle 11g 标识符
    30 字符上限，Cube 生成的 SQL 别名含 cube 前缀，过长报 ORA-00972 identifier
    is too long）；
17. **单独 `mask` 不生效**（P3 实测，docs/11 语义）：脱敏由 access_policy
    `member_masking` 激活，且**必须与 `member_level` 同一条策略**——
    `member_level: excludes: [X]` + `member_masking: includes: [X]` → X 对
    所有人脱敏；高度敏感字段（手机号/银行账号）不建维度，暴露面最小化。
18. **设计文档的表名是 ClickHouse/指标 YAML 侧叫法，建 cube 前必须 db.js 核实
    Oracle 实表**（P4 再次出现：fbe_stock_out/fbe_stock_in Oracle 不存在，
    实为 UBE_STOCK_OUT/UBE_STOCK_IN；同 P0 的 cbill 勘误模式）；
19. **Cube 有 join 必须有 primary_key**（P4 踩坑：stock cube 的源是视图
    V_UBR_STOCK 无 FID，编译报 "primary key is required when join is
    defined"——用 5 列键拼接合成主键（CONCAT + AS SID，唯一性先 db.js
    验证 488=488/190=190））；
20. **状态/结果码存在字典外复合码时原样分组，不做翻译假设**（P4 实测：
    FCHANGESTATE 61/64/31/541/521、FRESULT 3——列注释只写部分取值，
    state/result 维度按原值分组并在 description 记录实测分布）；
21. **业务同一单的多表副本不重复建 cube**（P4 核实：UBE_STOCK_RECEIVEAPPLY
    30 行全部是 UBE_STOCK_APPLY 同一单的接收副本，FAPPLYID→FID 100% 命中、
    票号一致——UNION 会重复计数，只建 APPLY 一个）。
22. **多事实视图（multi-fact view）混查跨 view 不可 join**（P5 实测：一次查询
    混三个 view 的度量报 "Can't find join path to join 'suspicious', 'paybook',
    'cbill'"——不同主题的事实无 join 路径，逐 view 分开查）；
23. **多事实视图的孤儿明细行被丢弃**（P5 实测：writeoff_view 的 item_amt/
    face_amt 略小于明细 cube 全量——income/billitem 孤儿行 join 不上主表，
    混合查询时不计入；单查明细口径走明细 cube，ai_context 写明）；
24. **view 的 join_path 必须显式、同名成员必须精选规避**（P5 实测：suspicious
    有 agency+region+bill_type 三 join，view 未含 region 时 region_name 下钻
    报 "not found"；region.name 与 agency.name 冲突用 prefix: true 解决——
    但 prefix 会拼长别名，11g 30 字符上限下优先精选规避）。
