# 问数五步规程（S1–S5）

> 状态：**规程稿**——2026-10-12 定稿。把自然语言查数问题转换为语义层可执行的 query JSON，或在不可执行时给出转办结论。
> 挂载点：cube-ask 主链四步的第 2 步（解析生成 query）。
> 配套：口径词典（`GET /agent/dictionary`，存档 `conf/agent/dictionary.json`）、三个交付 view 的 `ai_context`（`conf/model/views/*.yml`）
> 鉴权：数据来源为 Cube :4000 的 `/agent/*` 契约接口，除 `GET /agent/tools` 外一律 `Authorization: Bearer $CUBEJS_API_SECRET`（token 取法见 skill 第 1 步）；原生 `/cubejs-api/v1/*` 不走。

---

## 一、定位

| 项 | 内容 |
|---|---|
| 输入 | 自然语言查数问题 |
| 输出 | query JSON（成员全名引用，filter 仅 `{member, operator, values}` 形态）或转办结论 |
| 执行前提 | meta 与口径词典可获取（见 S1 输入） |
| 失败处置 | 失败原子不进入后续步骤，单独输出并附原因，禁止构造近似查询替代 |

## 二、五步规程

### S1 口径原子化

- **输入**：
  1. 自然语言问题；
  2. 成员清单与口径文案，固定来自两处：
     - **接口** `GET /agent/meta` / `GET /agent/meta/{topic}`——返回各 view 全部成员：measures / dimensions 的 name、title、成员类型，各成员 `description`，view 的 `ai_context`；
     - **词典** `GET /agent/dictionary?term=`——业务口径中文对照。
- **过程**：
  1. 按并列标记（顿号、逗号、"以及"）拆子问句，每个子问句恰含一个数量词；无数量词的为省略语境，结合上文补全或终止确认；
  2. 逐子问句**直达识别**三元组，各槽位对照 meta 清单与口径词典直接落点，不经过中间归类表：
     - **主语事实** ← 业务实体名词，保留原文、不翻译、不路由（路由是 S2 职责）；
     - **度量语义** ← 数量词的自然语义（笔数 / 单据数 / 金额 / 实物量），并按 meta 中度量 title/description 预判落点成员方向；成员全名的绑定是 S3 职责；
     - **约束** ← 限定语的约束形态（状态过滤 / 时间窗 / 分组），仅记形态与原文值；成员全名的绑定是 S4 职责。
- **输出**：原子集合 `[{主语事实, 度量语义, 约束}]` + 计算规格清单（可拆计算型：`{算式, 原料原子引用}`）。
- **规则**：
  1. 度量语义四类（笔数 / 单据数 / 金额 / 实物量）之外的诉求为计算型，按可拆性分路：可拆为「原料诉求 + 算式」的 → 按**算式模板库**（下表）生成**计算规格**（原料原子 + 算式），原料原子照常进入 S2——命中模板的直接套用，原料原子与时间错位按表自动生成，不逐次推断；模板未覆盖的可拆计算型按"原料 + 算式"现拆；不可拆的（分位数；聚合输入为不存在的行级派生列，如跨列日期差的平均）→ 标记计算型直接交 S5；

     **算式模板库**：

     | 算式 | 原料原子模式 | 时间错位规则 |
     |---|---|---|
     | 同比 | 两个同构原子（同主语、同度量、同约束，仅时间异） | 本期年 N 与 N−1；本期为相对词（"今年"）时原文登记，错位换算交 S5 判定项 5 |
     | 环比 | 两个同构原子 | 相邻月 / 相邻季 |
     | 占比 | 分子原子 + 分母原子（分母常为全量、无 filter） | 同窗口 |
     | 差值 | 两个原子（同度量，约束或时间不同） | 同窗口 |
     | 均值（总额÷笔数式） | 金额原子 + 笔数原子 | 同窗口 |
  2. 槽位无法填充且无法从上文补全 → 标记「待确认」，不得凭空补值；
  3. 主语不同的原子保持独立，是否可合并到 S2 路由后复核；
  4. 识别落点与 meta / 口径词典冲突时（量词指向模型不存在的度量语义）→ 按「待确认」处理，不得迁就问题改口。

### S2 主语路由

- **输入**：
  1. S1 输出的原子集合；
  2. view 语义域信息，固定来自两处（与 S1 同源）：
     - **接口** `GET /agent/meta` / `GET /agent/meta/{topic}`——各 view 的 title、description、`ai_context`（语义域分工与口径文案，如 treasury 的 ai_context 首句"缴库入库视图，一行一笔缴库明细（缴库单×科目）"即名词域锚点）；
     - **词典** `GET /agent/dictionary`——业务名词归属对照。
- **过程**：
  1. 逐原子取「主语事实」名词与约束值，对照各 view 的 title / description / `ai_context` 文案及口径词典词条匹配；命中唯一 view → 写入路由标签，成员搜索域收缩为 meta 中该 view `includes` 的成员清单（S3/S4 仅在此清单内选成员）；
  2. 名词命中多个 view → 按序消解：① 约束值线索（如"已入国库"仅出现在 treasury 的 ai_context 语境）② 原子内修饰语 ③ 仍歧义 → 标记「待确认」，不得默认；
  3. 名词在两处来源均无匹配 → 终止，向提问方确认业务含义；确认产生的新名词**先 `POST /agent/dictionary` 回写补录**（`{term, cube, rule}` 必填，upsert by term；涉及口径分工的同步补入对应 view 的 `ai_context`，走 cube-modeling），**再重新路由**，禁止临时推断；
  4. 单原子需多数据域支撑 → 不强行路由，标记跨表，交 S5 第 3 项判定。
- **输出**：带路由标签的原子集合 `[{主语事实, 度量语义, 约束, view}]`。
- **规则**：
  1. 路由一对一，一个原子恰对应一个 view，跨域诉求一律拆解为多原子或转 S5，不存在混合路由；
  2. 路由失败（无匹配/歧义未消/跨域）的原子不进入 S3，单独输出并附失败原因；
  3. 匹配依据仅限上述两处来源，禁止凭会话记忆或常识推断路由。

### S3 度量绑定

- **输入**：
  1. S2 输出的带路由标签原子集合；
  2. 度量成员信息，固定来自两处（搜索域已由 S2 收缩至该路由 view）：
     - **接口** `GET /agent/meta/{topic}`——该 view 的 measures 清单：name、title、description，以及各成员的**聚合类型**（count / countDistinct / sum / max / avg / min；接口不单独透出，依据 title / description / `ai_context` 口径文案判定）；
     - **文档** 该 view 的 `ai_context`（`conf/model/views/*.yml`）中的度量口径文案；`GET /agent/dictionary` 作业务名词对照。
- **过程**：
  1. 按「度量语义」在搜索域内以**聚合类型**筛选（机判，不经分类表；聚合类型依据成员 title / description / `ai_context` 口径文案判定）：笔数 → 计数类（count）；单据数 → 去重计数类（countDistinct）；金额 → 求和类（sum）；实物量 → 受限可加成员（见规则 3）；
  2. 候选唯一 → 绑定成员全名（view 限定名，如 `fiscal_treasury_view.count`）；候选多个 → 用原子的修饰语/约束值对照成员 title / description 与 `ai_context` 口径文案消歧（如"缴款金额" amt vs"到账金额" entered_amt）；仍无法消歧 → 列出全部候选并附口径差异，标记「待确认」；
  3. 粒度两可（笔数 vs 单据数）→ 按该 view `ai_context` 的粒度口径文案判定（treasury 已写明：缴库单数用 bill_count，明细笔数用 count）；文案未覆盖 → 两者均输出。
- **输出**：原子 + 度量成员全名。
- **规则**：
  1. 成员绑定仅限 S2 搜索域（该 view `includes` 清单），禁止引用 cube 层未进 view 的成员；
  2. 金额诉求仅接受聚合类型为求和（sum）的度量——聚合类型为单笔最大/平均/最小（max / avg / min）的金额成员自动排除在候选之外（机判，不依赖逐名记忆）；其使用场景仅限明细下钻（drill_members）；
  3. 实物量成员（如 `exec_qty`）仅当查询含对应计量单位维度分组时可选，否则按「待确认」处理；
  4. 语义落点在搜索域内无对应成员（如量词指向 view 未覆盖的度量语义）→ 按「待确认」处理，不得迁就问题改口，也不得跨 view 借成员。

### S4 约束绑定

- **输入**：
  1. S3 输出的原子 + 度量成员全名；
  2. 约束成员信息，固定来自两处（搜索域已由 S2 收缩至该路由 view）：
     - **接口** `GET /agent/meta/{topic}`——该 view 的 dimensions 清单：name、title、description，以及各成员的**维度类型**（string / time；依据 title / description / `ai_context` 口径文案判定）；
     - **文档** 该 view 的 `ai_context`（`conf/model/views/*.yml`）中的时间轴与状态口径文案；`GET /agent/dictionary` 作业务名词与取值对照。
- **过程**：
  1. 按「约束」槽位形态在搜索域内以**维度类型**筛选（机判，与 S3 同构；维度类型依据成员 title / description / `ai_context` 口径文案判定）：状态/分类过滤 → 文本类（string）维度，按 title / description 与约束值匹配；时间窗 → 日期时间类（time）维度；分组诉求 → 文本类（string）维度中按"分别/各/按 X"的名词匹配；
  2. 候选唯一 → 绑定成员全名；候选多个 → 按该 view `ai_context` 的时间轴/状态口径文案消歧（treasury 实文："已入国库多少笔/金额……时间轴必须用 enter_date；缴库单量/日报趋势按 build_date，两者口径不同勿混用"）；仍无法消歧 → 列出候选并附口径差异，标记「待确认」；
  3. 取值绑定：枚举维度取值从 dimension `description` 复制，或取自口径词典词条；时间约束记原文值（"今天""近 30 天"），具体日期换算交 S5。
- **输出**：原子 + 约束成员全名与取值，按查询协议落位：状态/分类过滤 → `filters` 数组（`{member, operator, values}`）；时间窗 → `timeDimensions`（需要趋势时写明 granularity）；分组诉求 → `dimensions` 数组（`*_code` 管分组，`*_name` 仅展示，成对出现时以 code 为准）。
- **规则**：
  1. 成员绑定仅限 S2 搜索域（该 view `includes` 清单），禁止引用 cube 层未进 view 的成员；
  2. 枚举取值禁止推测：description 与口径词典均无取值 → 按「待确认」处理，不得猜值；
  3. 时间维度按 `ai_context` 口径绑定，不得互换业务含义不同的时间轴（如 enter_date vs build_date）；
  4. 相对时间词在 S4 只记原文、不换算——静态换算与窗口声明是 S5 第 4 项的职责。

### S5 可行性判定

- **输入**：
  1. S3/S4 绑定完成的原子集合（含度量成员全名、约束成员全名与取值）；
  2. S1 标记的**计算型诉求**清单（比率、平均、分位数等，未产生原子）；
  3. S2 标记的**跨表**原子清单。
- **判定依据（协议事实，全部机判）**：query JSON 合法字段集（measures / dimensions / filters / timeDimensions / order / limit）为成员引用制、无表达式求值位置；聚合类型封闭集（count / countDistinct / sum / avg / min / max，无分位数）；`timeDimensions.dateRange` 为静态日期数组；单查询成员必须同源（同一 view）。
- **判定项与处置**：
  1. **答案层算术**（比率、差值、总额÷笔数式平均——S1 已拆出计算规格）→ 正路，不转办。原料 query 按**合并规则**生成：
     - 原料原子同 view、**同度量、仅时间不同** → **合为一条 query**：timeDimensions 粒度分组取回多行（粒度与错位一致——同比取年、环比取月/季），每组即一个原料值；
     - 同 view、同度量、**filter 不同** → 拆为多条 query，每条带各自 filter；
     - 同 view、**度量不同** → 合为一条多度量 query；
     - **跨 view** → 各一条。

     运算在答案整理层完成。答案按以下规范输出：
     - **三件套**：原料、算式、结果齐报；
     - **方向词**：差值为负说「减少 X」，不说「增加 −X」；
     - **预设纠偏**：问题预设与结果方向相反时，显式说明实际方向（"不是增加，是减少"）；
     - **精度**：金额报元（两位小数）与万元双形态，百分比两位小数。

     守则：
     - 分子分母（或被减数/减数）的过滤与时间窗必须一致，不一致须在答案中声明；
     - **无记录 ≠ 0**：差值任一侧为空或分母为 0 / 空结果一律不硬算；空侧报「该期无数据」，分母侧报「分母无数据」；
     - 任一原料查询为空 → 补该时间轴全量分布查询（仅按时间粒度分组）定位根因，并在答案中声明（如"测试数据年份跳跃，2025 缺位"）。
  2. **行级派生列聚合**（聚合输入为不存在的行级派生列，如跨列日期差的平均）→ 查询表达不了 → 转模型层衍生度量（均值型聚合，建模 yml 写 `type: avg` + sql 表达式），建后热重载可查，注明原因；禁止拿别的成员冒充口径（近似替代仅在此档与第 3 档禁止）；
  3. **分位数聚合**（P95、中位数）→ 聚合类型封闭集无对应类型 → 明细导出后外部计算，注明处置方式；
  4. **跨宽表对照**（同一答案需并列 ≥2 个 view 的数字，含 S2 跨表标记，无算式）→ 拆分为多条独立 query + 拼接说明（拼接在答案整理层完成），禁止 join 表述；
  5. **动态相对时间窗口**（"今天""近 N 天"）→ `dateRange` 为静态数组 → 换算为具体日期区间，query 照常生成，答案中声明窗口边界。
- **输出**：无命中 → query JSON（单条或多条）；命中 1 → 原料 query + 算式；命中 2/3 → 转办结论（含原因与建议路径）；命中 4 → 多条 query + 拼接说明；命中 5 → query + 窗口声明。

## 三、贯穿示例

「今天新增开具多少笔、已缴多少笔、已入国库多少笔」

- S1 → 三原子：`{开具, 笔数, timeRange=今天}`、`{缴款书, 笔数, filter=已缴}`、`{缴库, 笔数, filter=已入国库}`（度量语义槽为自然语义，非成员名）；无计算型诉求；
- S2 → 前两者路由 `fiscal_collection_view`，第三者由约束线索（"入国库"仅出现在 treasury 的 ai_context 语境）路由 `fiscal_treasury_view`；原子 1、2 同 view 但口径不同（开票行为 vs state 过滤），保持独立；无跨表标记；
- S3 → 各原子在路由 view 的 measures 内按聚合类型筛选：度量语义均为笔数 → 计数类（count），collection 与 treasury 各唯一命中，分别绑定 `fiscal_collection_view.count`、`fiscal_treasury_view.count`；treasury 的粒度文案（ai_context："缴库单数用 bill_count，明细笔数用 count"）判定"多少笔"为明细笔数，排除 `bill_count`（聚合类型为去重计数 countDistinct）；
- S4 → 约束成员按维度类型筛选绑定：原子 1 时间窗 → 日期时间类（time）维度 `pay_date`（落 `timeDimensions`，当日区间）；原子 2 状态过滤 → 文本类（string）维度 `state`（落 `filters`，取值从 description 复制）；原子 3 状态维度 `enter_status`（取值 '1'，落 `filters`）+ 时间轴 `enter_date`（落 `timeDimensions`——ai_context 时间轴文案消歧："已入国库……必须用 enter_date"，排除 build_date）；
- S5 → 按判定依据逐项核对：三条 query 均为成员引用（无列间运算、无未注册聚合形态）；无分位数诉求；每条成员同源单 view（无跨表标记）；原子 1 的相对时间词"今天"按判定项 5 换算为具体日期区间，答案中声明窗口边界 → 产出三条独立 query。
