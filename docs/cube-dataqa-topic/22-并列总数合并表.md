# 22 并列总数合并表（一行多列）

> 2026-09-28 拍板。背景＝当日实测（`logs/bridge-2026-09-28.log:11530-12157`）：
> 问"今天新增开具多少笔、已缴多少笔、已入国库多少笔？"——三个并列总数被拆成
> 三张一行一列的碎表。根因＝17 号"答案需要几个口径就几张表"没有区分两种多口径
> 形态，把给分组明细表定的规则照搬到了并列总数上。
> 拍板结论：**一口气问了几个并列的总数，就把几个数并成一张表，一行几列**；
> 查询照旧各查各的，只把结果抄进同一行。
> 改动只有提示词（桥指令）和 skill 各一段话——无新字段、无新表形态、
> 桥代码零改动、前端零改动。

## 1. 说人话：要解决什么问题

用户问：**"今天新增开具多少笔、已缴多少笔、已入国库多少笔？"**

这是一句话里问了**三个并列的总数**。答案的自然样子是**一张表、一行、三列**：

| 开票笔数 | 已缴笔数 | 入国库笔数 |
|---|---|---|
| 0 | 0 | 0 |

但实际返回了三张表（每张一行一列）。原因：

- **契约层（主因）**：17 号"需要几个口径，就返回几张表"没有区分两种多口径形态——
  **同数据不同分组维度**（单位×项目 vs 单位×科目，两张多行明细表，多表正确）vs
  **同主语并列指标**（三个环节的当日计数，自然形态是一行 3 列）。agent 在
  thinking 里明确引用该契约输出 3 表（log:12023），**忠实执行、不是幻觉**。
- **技术层**：三个数来自三个互不 join 的 cube（`usage_view`/UNE_CBILL、
  `paybook_view`/UNE_PAYBOOK、`treasury_view`/UNE_AGEN_TREASURY），跨 cube 裸拼
  硬报错、硬造 join 数字不可靠（skill 第1步成员面实测）——**三条独立查询必然
  保留，合并只能发生在答案组装与呈现层**。

**新规则一句话版：一口气问了几个并列的总数，就把几个数并成一张表，一行几列。**
（"同主语并列子问且各口径单行聚合，结果表合并为一张"的直白翻译。）

## 2. 什么时候合、怎么合、什么不合

### 2.1 什么时候合（同时满足两条）

1. **并列子问**：一句话里几个同级的小问题，各要一个总数——像"今天 X 多少、
   Y 多少、Z 多少"这种日报式问法
2. **每个子问都是单行聚合**：每个口径只算一个总数，不按单位/票种/月份分组，
   返回各是一行一个数

### 2.2 怎么合

- 查询不动：每个口径各跑各的 query（独立查询，语义层本来也合不了）
- 组装答案时：把每个口径的**那个数**抄进**同一行**，键用度量成员名
  （列名就是成员名末段，接受原列名）
- 表级 `query` 填**第一条**口径的查询（「填入构建器」「固化」用它；三条拼一条
  是无效查询，禁止）
- `total` 置 null（三个独立口径没有占比分母，禁止跨口径合计）
- 表标题概括全部口径；口径声明逐列写清各自时间轴（开票日期/确认日期/缴款日期）
- 同一 cube 的多个度量本就一条 query 能出多列，不属合并，走普通路径

合并后的 JSON（前端现有代码直接渲染出一行三列）：

```json
{
  "title": "今日开票/已缴/入国库笔数（各自业务日期）",
  "query": { "measures": ["usage_view.receipt_count"], "dimensions": [], "filters": [],
             "timeDimensions": [{"dimension": "usage_view.bill_date", "dateRange": ["2026-09-28","2026-09-28"]}], "order": {}, "limit": 100 },
  "rows": [{"usage_view.receipt_count": 0, "paybook_view.paid_count": 0, "treasury_view.count": 0}],
  "total": null
}
```

渲染结果（现有代码，`ext-chat.js:328-333` 行内键出列）：

| receipt_count | paid_count | count |
|---|---|---|
| 0 | 0 | 0 |

### 2.3 什么不合（出现任一即不合，各表各的）

| 情形 | 例子 | 结果 |
|---|---|---|
| 任一子问要**分组**（返回多行明细） | "各单位收入明细 + 各单位缴库明细" | 仍 N 张表，17 号平等渲染 |
| 子问间**不是并列关系** | 有主次、有先后依赖的口径 | 各表各的 |
| 混着来（有的要总数、有的要分组） | "总笔数 + 按单位明细" | 不合，各表各的 |
| 同一 cube 的多个指标 | "正常票和作废票各多少" | 一条查询出多列，不涉及合并 |

## 3. 改动的是提示词、skill 还是代码

**只有提示词和 skill 各加一段话，代码零改动。**

关键洞察：合并表**结构上就是现有"多度量表"形态**——单 cube 多度量一条 query
（如 `receipt_count`+`normal_count`+`void_count`）今天就渲染成一行多列；跨 cube
合并表产出的 JSON 与它完全相同。所以前端、`_normalize`、固化、构建器、qa-log
全部零改动，唯一的新东西是**指令里一段话**（告诉 agent 什么情况下按这个方式组装）。

## 5. 方案演进记录（讨论史实，防复翻）

- **初版设计**：agent 打标记字段（mergeGroup/groupTitle/columnLabel）+ 桥新增
  `_merge_groups` 纯函数确定性拼行 + 前端加 columns 中文表头。
- **收敛 1（前端拍板零改动）**：发现 `renderTable` 的行内键尾插兜底
  （`ext-chat.js:330-333`，原为漂移防御）正好能渲染合并表 → 删 columns/中文表头，
  接受英文成员名列名。
- **收敛 2（`columnLabel` 成死字段）**：前端零改动后无人消费 → 删，标记收缩为
  mergeGroup/groupTitle 两个。
- **收敛 3（去掉标记与桥函数，本稿定稿）**：两个论据——
  ① 合并表结构上与现有"单 cube 多度量表"完全相同，无需新契约表面；
  ② 桥拼行"零抄错"经复算不成立：两种设计里 agent 都要从工具结果抄 N 个值进
  JSON，抄数环节一样多，桥合并防的是边界违规不是值错误，而该违规渲染上优雅
  退化。按 `_normalize` 文化（观察到的漂移才兜底），未观察到的失败模式不预建
  gate。改动面从"桥函数+3 字段+前端"缩到"两段指令文案"。
- 残余风险：语义边界（并列子问判定）是 agent 判断，无机械 gate——靠 plan 可
  追溯 + qa-log 可复算 + 渲染优雅退化兜底。
- **收敛 4（执行期发现，2026-09-28）**：会话期间 14 号 §4.1 R3 桥单写落地——
  qa-log 由桥从 agent 最终输出的 JSON 机械派生（`_qa_log_answer`），agent 零写。
  影响：本稿原"约束 5 括注 / SKILL 日志模板括注 / qa-log queries 3 条"三个落点
  作废或调整——合并表日志 `queries` 记首条一条，逐口径复算靠同行 plan（成员+
  时间轴完整）；若事后审计发现不够，再议升级 `_qa_log_answer`（遗留观察项，
  不预建）。
