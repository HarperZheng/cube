## 0. 收益：一次 15 分钟/cube 的盘点，换什么

| 面 | 没有清单（现状） | 有清单 |
|---|---|---|
| **问数撞缺口（失败模式 d）** | 答不了"源表到底有没有这列"——要确认就得转 modeling 开流程核查源表，分钟到天级 | 一条命令即知（`unmodel.js show`）："业务储备：FOWNIMAMT（本级金额）"——源表有料、可补建。话术从"我不确定，要核查"变成带证据的"支持，补建约几分钟" |
| **FSUB\* 式事故（16 号全案）** | 真业务列静默缺席 → agent 答"查不了" → 用户拍板绕路（双口径 workaround、跨事实表拆分）→ 事后排查才发现源表自带列，再返工 | daybook 的 14 列业务储备列（资金性质/主管部门/预算单位/直缴汇缴/本级金额/缴款码……）全部有交底——同类事故从根上堵住 |
| **建模原料核实（分支② / ③-1）** | 每次补建都 user_tab_columns 全列重扫、逐列读注释定性 | 分类结论直接复用；新列 survey 暂归 reserve 待人工归类 |
| **接手/审计** | 30 列缺席是黑洞，"没建模"与"没看见"不可区分 | 每列有交代、可审计；新人/新 agent 查一册 JSON 即得全貌 |
| **成本** | — | 一次性 15 分钟/cube（§7 流程），独立 JSON 零编译风险、Cube 升级零关联（§2） |

一句话：**把"没建模"与"没看见"变成可区分**——问数答得更准、补建走得更快、缺席有交代。

## 1. 是什么 / 不是什么

**是**：每个事实 cube 一册的「源列 → 建/未建/原因」**机器可读登记**——JSON 存储、
schema 约束（类别枚举）、工具层（survey / show，§4）。

**不是**：

- **不在 yml 里**——独立于 `conf/model/`，Cube 编译器 / schema 校验 / 官方升级全程零关联
  （2026-09-27 拍板：不修改 yml 格式定义，注释方案也一并废弃）
- **不复制已建列**——已建列的唯一真相是 yml 成员的 sql 引用；
  清单里的 `totals` 只是**断言**，不是第二份维护点（补建后重跑 `survey` 即重算更新）
- **不是纯文档**——独立 JSON 机器可读、`survey` 机械算差集生成/更新（非手维护文本）；
  无硬门（check 撤回，2026-09-28：漂移靠下次 survey 收敛，遗留观察项）
- **不辖整表未建模（2026-09-29 拍板）**——清单是"进过 model 的表"的对照账：
  差集锚点（yml 已建列）与 redundant/id_key 的分类判据（快照 vs join 落败者、
  join 键已用）都以建模决策为前提，整表未建模时两者皆无——那是**缺席主题**
  （失败模式 d 三档落 ③），不是缺席列；原料现查 `db.js find/cols`

## 2. 存储结构（拍板：`conf/unmodel/<cube>.json`）

**目录名 `unmodel` = 未建模（un-modeled）**，与 `conf/model/` 平级成对照：
`model/` 放已建的，`unmodel/` 登记未建的。每事实 cube 一册：

```
conf/
  model/          # Cube 扫描（schemaPath），已建模型——清单不碰这里
  unmodel/        # Cube 不扫描（不在 schemaPath 下，且 Cube 只认 schemaPath 内 yml/js）
    daybook.json
    treasury_item.json
    ...
```

容器可达性（零 compose 改动）：compose 挂载是整目录 `- ./conf:/cube/conf`，
`conf/unmodel/` 自动出现在容器内 `/cube/conf/unmodel/`——容器内 `unmodel.js` 直接读写。

JSON 结构（daybook 缩略示例，完整首例见 §8）：

```json
{
  "schema": "unmodeled-inventory/1",
  "cube": "daybook",
  "source_table": "FNE_INCOME_DAYBOOK",
  "surveyed_at": "2026-09-27",
  "totals": {"source": 56, "built": 26, "unmodeled": 30},
  "trigger_semantics": {
    "technical": "系统流程/预留字段——不主动建；口径排查发现依赖时再评估",
    "id_key": "识别码，编码/名称已建或走 join——查询成员永不建；join 在声明里用",
    "redundant": "快照与 join 二选一落败者——口径争议时重评 join vs 快照",
    "reserve": "真业务语义、暂无消费场景——问到即 cube-modeling 分支②补建"
  },
  "entries": [
    {"column": "FOWNIMAMT", "comment": "项目收入金额(本级)", "category": "reserve"},
    {"column": "FSUBID", "comment": "收入科目Id", "category": "redundant",
     "note": "快照列族孤悬 ID（FSUBCODE/FSUBNAME 已建）；join 方案已评估弃用"},
    {"column": "FIMAGENIDCODE", "comment": "收入单位识别码", "category": "id_key",
     "note": "join 键已用未作成员"}
  ]
}
```

设计要点：

- **entries 扁平、一列一行**——git diff 里每列独立成行，补建划掉、新增入册原子可见
- **只存未建列**（差集）；`totals` 三数都是断言，由 `survey` 重跑即重算更新（无 check 硬门）
- **类别是枚举**（§3 四类，2026-09-28 拍板）；`trigger_semantics` 进结构——每册自包含，
  读清单的人（agent 或人）不需要翻本文档就知道行动指引
- 维护规则：分支②补建某列后跑 `survey`（自动把已建列提出待删、更新 totals）；
  源表将来加列 → 下次 `survey` 盘点时入册（暂归 reserve，无 check 硬门，遗留观察项）

## 3. 四类分类学（判据 + 触发语义；2026-09-27 五类拍板，2026-09-28 四类定稿——明细追踪并入业务储备）

设计原则：**类别名 = 不建的原因；每类背后挂一个"什么情况下会建"的触发语义**。
翻清单的人（agent 或人）扫一眼类别就知道这列值不值得抱期望、该走哪条路。

| 类（枚举键，2026-09-28 已定稿） | 判据（为什么不建） | 触发语义（什么情况下会建） |
|---|---|---|
| **技术列** `technical` | 系统流程/预留字段：版本、变更标志、生成标志、批次号、FCUSTOM\* 自定义扩展空列——无业务语义 | 几乎永不建；口径排查发现暗中依赖它时再评估 |
| **ID/内部键** `id_key` | 识别码/代理键；对应编码/名称列已建或走字典 join | 作为**查询成员**永不建；join 需要时在 join 声明里用 |
| **冗余** `redundant` | 源表自带的字典字段快照，与 join 方案二选一后的落败部分 | 口径争议时**重新评估** join vs 快照（daybook sub_name 即翻案先例） |
| **业务储备列** `reserve` | **真业务语义**，只是暂时没人问 | **问到即 cube-modeling 分支②补建**——FSUB\* 事故的原生类别，清单价值的最大来源；原明细追踪类并入（缴款码等单据级流水码，明细下钻场景出现时建，大概率进明细粒度） |

三条边界规则（归类拿不准时用）：

1. **FCUSTOM\* 自定义扩展空列** → 技术列，批量一行带过（"系统预留空列"）
2. **语义不明/列注释自相矛盾** → 暂归业务储备列，疑点写 note（无独立标注机制，
   2026-09-28 撤回——简化开发）；核实后改类或补建——让"不知道"诚实可见，不硬塞
3. **冗余 vs ID 键**：快照列族的其他成员已建、剩它孤悬（如 FSUBID）→ 冗余；
   从来没有对应建过任何成员 → ID/内部键

## 4. 工具：`agent/unmodel.js`（survey / show）

第三个工具层脚本（与 cube.js / db.js 平级），随既有挂载 `- ./agent:/cube/agent`
自动进容器，零 compose 改动。形态已随实施定为独立文件（2026-09-29，§6 #1 关闭）。

两个命令的读写面——`show` 是唯一不碰 Oracle / yml 的纯消费命令：

| 命令 | 读什么 | 写什么 |
|---|---|---|
| survey | Oracle user_tab_columns（源列全集）+ conf/model/*.yml（已建 sql 引用） | 生成/更新 conf/unmodel/<cube>.json |
| show | 仅 conf/unmodel/<cube>.json | 无（打印，可 --category 过滤） |

```bash
# 盘点（半自动）：Oracle user_tab_columns + 解析 yml 成员 sql 引用 → 算差集 → 生成/更新骨架
#   新出现的源列暂归 reserve（人工归类后定稿）；已建列自动提出待删；人工分类过的条目保留不动
docker exec cube sh -c "node /cube/agent/unmodel.js survey daybook"

# 消费（人/agent 查询）：可按类别过滤
docker exec cube sh -c "node /cube/agent/unmodel.js show daybook --category reserve"
```

**辖域边界（survey 行为，2026-09-29 拍板）**：survey 是 cube 键控（cube 名 → yml
`sql_table` → 源表）。cube 不存在于 conf/model 时**报错退出**——提示"整表未建模
走 cube-modeling 分支③，原料现查 `db.js cols`"；**不按表名建全 reserve 假册**
（差集 = 全集、分类无对照物）。表进 model 的时点即首册时点（③-5 第 3 项）。

**无 check 硬门**（2026-09-28 撤回，不给建模加压）：漂移风险 = 补建后忘跑 survey →
陈旧条目误报未建——低害自愈：撞缺口时已建列一眼识破，重跑 `survey` 即收敛；
源表新列缺席则退回现状话术（不比没有清单更差）。作遗留观察项，对齐 22 号收敛 3
（未观察到的失败模式不预建 gate）。

集成点：modeling 分支②补建后跑 `survey` 更新清单（维护纪律，非 gate）；分支③-5 新 cube 交付
同步产出首册。
