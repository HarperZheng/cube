# 17 多口径表前端渲染（tables 平等契约）

> 2026-09-27 拍板。背景＝16 号文档 §2.2 事故：多口径答案的次口径只存在于 answer
> 文本，前端 renderAnswer 从不渲染 answer → 占比列与 B 口径整表不可见。
> 拍板结论：**废除主/次口径概念**——答案需要几个口径，就返回几张表，每张表自带
> 标题、query、行、占比分母，结构完全对称；没有谁是"主"，没有谁藏在文本里。
> 本文档＝契约定义＋前端渲染设计＋执行方案，含两个已定决策：`data` 字段彻底删除、
> qa-log 加 `queries` 数组。

## 1. 原则：口径生而平等

- 旧契约（09-24 收紧，11 号 §6）：`data` 只装主口径扁平行，其余口径进 answer 文本
  markdown 表。它能修"嵌套 data 渲染坏"，但把口径分了主次——次口径进了一个前端
  不读的字段，等于看不见。
- "主口径"是伪概念：用户拍板"两种口径都出"之后，口径间没有主从关系，只有不同的
  分组维度。契约层面分主次＝制造一个天然丢数据的槽位。
- 一句话版：**需要几个口径，就返回几张表。**

与建模线正交：补建模让本案例收敛为单表（16 号 §6，那是"口径合一"），源表限制合不了
的（缴库口径无项目列）就多表平等返回（本文档）。合一后走 tables 长度 1 的同一条
代码路径，没有"单口径特例"。

## 2. 契约定义

### 2.1 answer 三态新形态

```json
{
  "type": "answer",
  "title": "各单位各预算科目下各项目收入金额及占比",
  "plan": [["自然语言", "cube.member", "依据"]],
  "tables": [
    {
      "title": "口径A：单位×项目（收入日结）",
      "query": {"measures": ["daybook_view.income_amt"], "dimensions": ["daybook_view.chg_agen_name", "daybook_view.item_name"], "filters": [], "timeDimensions": [], "order": {}, "limit": 100},
      "rows": [{"daybook_view.chg_agen_name": "某单位", "daybook_view.item_name": "某项目", "daybook_view.income_amt": "12345.67"}],
      "total": 30200711.05
    },
    {
      "title": "口径B：单位×预算科目（缴库）",
      "query": {"measures": ["..."], "dimensions": ["..."], "filters": [], "timeDimensions": [], "order": {}, "limit": 100},
      "rows": [],
      "total": 33222
    }
  ],
  "answer": "口径声明＋歧义拍板结论＋数据范围（表格数据不进文本）",
  "assumption": "...",
  "rows": 96,
  "truncated": false,
  "hitPreAgg": null
}
```

字段语义：

| 字段 | 语义 | 说明 |
|---|---|---|
| `title`（答案级） | **概括整个答案**的一句话（≤30 字） | 15 号 §16 修订：不跟主口径；多口径时覆盖全部口径 |
| `tables[].title` | 表级标题 | 写清口径身份（「口径A：单位×项目」式或自然语言）；固化默认标题用它 |
| `tables[].query` | 该表可执行 query | 「填入构建器」「固化看板」都按表取 |
| `tables[].rows` | 该表扁平行数组 | 原三条禁令平移：成员名键、一行一对象、禁 `{scope,rows}` 嵌套 |
| `tables[].total` | 该表占比分母 | agent 第5步铁律 2 原文：不带 dimensions 的全量查询拿，禁把截断行加总；`null` 则该表不出占比列 |
| `answer` | 纯口径声明、拍板结论、数据范围、截断说明 | **markdown 表废除**——数据只走 tables |
| `rows` | 全部表行数之和 | 脚注汇总 |
| `truncated` | 任一表可能截断即 true | 表级截断由该表 `rows.length == query.limit` 推断，表脚注按表标 ⚠ |

- 答案级 `query`/`data` 字段**删除**（单表信息全在 `tables[0]`）。
- 跨口径不做合计（09-27 用户拍板）：占比只在表内算，每表独立 total。

### 2.2 已定决策（2026-09-27）

| 决策点 | 结论 | 理由 |
|---|---|---|
| `data` 字段去留 | **彻底删除** | 前端（ext-chat/ext-publish）是唯一消费方，一起改；demo 阶段无兼容包袱；保留双字段＝保留"哪个是主"的歧义 |
| 漂移兜底 | `_normalize`：无 tables 有 data → 包装 `tables[0]`（query 取答案级 query 残留，total 置 null），stderr 留痕 | LLM 输出漂移不静默，前端单路径渲染 |
| qa-log 多口径 | **加 `queries` 数组**（每表一条）；`query` 保留记首表，过渡期后读侧迁 `queries` 再删 | 只记一张丢审计信息；避免读侧未迁先断 |
| 词典「各单位」两口径词条 | 维持不动 | 歧义处理协议与契约正交，照旧运作 |

## 3. 前端渲染设计（playground-ext/ext-chat.js）

### 3.1 renderAnswer：N 表平等

```
renderAnswer(d):
  renderPlan(d.plan)                      // 计划表全答案一张，不变
  for each t in d.tables:
    表卡片 div（容器）:
      <div class="ext-chat-ttitle"> esc(t.title) · t.rows.length 行 [⚠ 可能截断]
      renderTable(t.query, t.rows, t.total)   // 占比列见 3.2
      [固化此表] [填入构建器]                 // 表级按钮，见 3.3
  assumption（口径声明）→ foot（rows=Σ、truncated、hitPreAgg）
```

- 表卡片容器自带 `data-ext-query` / `data-ext-title`（该表的 query/title）——
  消息级同名载体废止（消息 div 不再挂）。
- 消息级「在构建器中打开」按钮移除（表级按钮覆盖其功能，避免双入口歧义）。

### 3.2 renderTable：占比列

- 签名 `renderTable(query, rows, total)`；列序改为 dimensions 先、measures 后
  （按 query 排序，不再依赖首行键序）。
- **占比列规则**：表内唯一度量且 `total` 非 null 时，度量列右追加「占比」列＝
  `Number(v)/total*100` 两位小数；多度量表不加（防列爆炸，需要时 agent 拆表）。
- **前端只做除法**：分母用 agent 提供的 total（skill 第5步铁律 2 的前端镜像）——
  截断时自行加总是错的，这条纪律不因计算搬到前端而放松。

### 3.3 表级固化（ext-publish 联动）

「固化此表」点击 → 沿表卡片容器取 `data-ext-query`/`data-ext-title` → ext-publish
`openDialog(q, title)`；对话框默认标题＝表级 title（15 号 §16 修订），
回退链不变（title 缺失 → annotation 拼接，`defaultTitle()` 一行不动）。

> ⚠ 动手前必读：先核实 ext-publish.js `injectPubBtn()` 现在怎么发现/读取消息级
> 载体（扫描属性还是点击时取），表级化按它的实际机制改，别按本文档想象改。

### 3.4 兜底与回退

| 场景 | 行为 |
|---|---|
| tables 正常 | N 表渲染＋表级固化/构建器 |
| 桥 `_normalize` 包装的漂移 data | tables[0] 单表渲染（total=null → 无占比列，宁缺毋错） |
| tables 空且 answer 有文本 | 渲染 answer 文本兜底（answer 从"永不渲染"变"无表时兜底"） |
| 旧消息卡 | 聊天不持久化，页面刷新即消失，无兼容问题 |

## 4. 桥侧改动（chat/chat_server.py）

1. **约束 3 重写**：tables 模板替代 `query`+`data` 单表形态；三条数据纪律从 data
   平移到 `tables[].rows`；`tables[].total` 取数纪律＝第5步铁律 2 原文；answer 职责
   改为纯声明；title＝概括整个答案（15 号 §16 修订同步落进指令文案）。
2. **约束 5 附注**：qa-log 多口径时记 `queries` 数组（每表一条），`query` 保留记首表。
3. **`_normalize` 升级**：action→type 映射保留；data 嵌套展平逻辑保留（作用于漂移
   包装前）；新增"无 tables 有 data → 包装 tables[0]"兜底，stderr 留痕。
4. **生效边界**：新契约只对新会话生效（`--resume` 续轮的上下文还是旧指令）——改完
   重启桥进程即清（`_SESSIONS` 内存态，重启＝全部新会话，无需等 30 分钟 TTL）。

## 7. 修订：并列总数合并表（2026-09-28）

> 本契约的分叉补充，不推翻"口径生而平等"。完整设计与演进记录见
> [22-并列总数合并表.md](22-并列总数合并表.md)。

- **分叉规则**：同主语并列子问（一句话几个同级小问题，各要一个总数，日报式问法）
  且各口径单行聚合（无 dimensions）时，tables 只返回**一张合并表**——一行多列，
  列=各口径度量成员名（列名=成员名末段，接受原列名）；表级 query=首条口径的
  完整 query；total 置 null（跨口径无占比分母，禁止跨口径合计）。任一子问带
  dimensions（多行明细）就不合，本契约 N 表平等渲染照旧。
- **结构零新增**：合并表在结构上就是现有"单 cube 多度量表"形态——renderTable
  行内键出列（§3.2 描述的兜底，ext-chat.js:330-333）天然覆盖，前端、
  `_normalize`、固化、构建器零改动。改动只有桥指令约束 3 一段话 +
  skill 第6步一句（22 号 §3）。
- **审计（14 号 R3 桥单写口径下）**：合并表 qa-log 行 `queries` 记首条口径
  一条；全部口径的成员与时间轴在同行 `plan` 数组里完整可追溯（逐口径可复算）；
  rows=渲染行数（合并表计 1）。若事后审计发现首条+plan 不够用，再议升级
  `_qa_log_answer`（22 号 §6 记为遗留观察项，不预建）。
