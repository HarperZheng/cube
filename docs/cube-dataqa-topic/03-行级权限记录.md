# 03 行级权限最终方案：access_policy 双互补策略

> P2 阶段行级权限（原占位符 `{t.frgncode#in#getUserRegionCode()}`，语义为
> "有区划属性按行收窄、无属性看全量"）的最终落地。
> 配套：[01-design.md](./01-design.md) §7、[02-p0-p1-记录.md](./02-p0-p1-记录.md) §4 约定第 8 条。

---

## 1. 定义（paybook.yml 现行版）

```yaml
access_policy:
  # 有区划属性：按行收窄
  - group: "*"
    conditions:
      - if: "{ securityContext.region_code }"
    row_level:
      filters:
        - member: region_code
          operator: equals
          values: ["{ securityContext.region_code }"]
  # 无区划属性：显式放行全表
  - group: "*"
    conditions:
      - if: "{ not securityContext.region_code }"
    row_level:
      allow_all: true
```

## 2. 原理

**Core 硬语义：策略存在 = 白名单制**——cube 上声明了任何 access_policy，
未命中任何策略的用户被整表拒绝（生成 `WHERE (1 = 0)`，`rlsAccessDenied`），
**不回落默认全行**。因此"conditions 缺失 → 策略视同不存在 → 回落默认"的
单策略写法不通。

解法：**同一 cube 写两条互补条件的策略**——有区划属性走 `row_level` 过滤，
无属性走 `conditions: not securityContext.region_code` + `row_level:
allow_all` 显式放行。`allow_all`（docs/11 参数）恰好补上"如同不存在"的
空档，两条策略分别覆盖"有属性/无属性"两种状态，逻辑上完备。

## 3. 实测四种场景（模型热重载后，全部通过）

| 请求 | 期望 | 实际 | 命中策略 |
|---|---|---|---|
| 无 JWT | 7255 | **7255** ✓ | 第二条（allow_all） |
| JWT `{region_code:'530100'}` | 30 | **30** ✓ | 第一条（过滤） |
| JWT `{region_code:'530102'}` | 16 | **16** ✓ | 第一条（过滤） |
| JWT `{user_id:42}`（有上下文但无 region 属性） | 7255 | **7255** ✓ | 第二条（allow_all） |

## 4. 运维注意

- access_policy 定义在 **model 文件里，保存即热重载**，改后无需重启；
- 用 Playground **Security Context 按钮**即可验证两种上下文，无需签 JWT；
- 若需手工签测试 JWT：用 `node agent/cube.js secret` 取的**最新** apiSecret
  （**每次容器重启重新生成**，旧 secret 签的 token 签名无效，securityContext
  解析失败时**无报错、静默不过滤**）；
- 查询 view 时 cube 行级规则与 view **叠加生效**（docs/11）——P5 建 view
  后本方案零改动。

## 5. 沉淀

1. **"策略存在 = 白名单制"是 Core 的硬语义**：任何 access_policy 场景下
   都要保证"每种用户状态至少命中一条策略"，否则未命中的用户被整表拒绝；
2. 后续各主题事实 cube（P3 cbill、P4 stock 系列）若需同类行级权限，复制
   双互补策略块到各 cube（或 P5 统一上移到 view 层）；
3. `row_level.allow_all` 是"无属性放行"的关键参数——单策略 + conditions
   表达不了条件放行，必须靠互补的第二条策略兜底；
4. query_rewrite（程序化）是"声明式表达不了"场景的兜底（docs/11 定位），
   本项目暂无此类场景。
