# 主数据说明（Master Data）——为什么主数据做 dims 维度 cube

> 状态：概念说明（配合 [01-design.md](./01-design.md) 阅读，回答"§4 维度 cube 为什么只有 5 个、为什么是它们"）
> 数据来源：`YN0411` schema 实核（agent/db.js），表名均为 Oracle 实际表

---

## 1. 什么是主数据

主数据（Master Data）是**描述"业务中相对固定实体"的数据**——谁（单位）、什么（票种、项目、科目）、哪里（区划）。它回答"**是什么**"，而不是"**发生了什么**"。与之相对的是**交易数据（事务数据）**：每一笔缴款、每一次开票、每一次领票——回答"**发生了什么**"。

| | 主数据（维度表） | 交易数据（事实表） |
|---|---|---|
| 本系统例子 | `FAB_AGEN`（单位）、`FAB_BILL`（票种）、`FAB_ITEM`（收费项目）、`FAB_SUBJECT`（科目）、`AFA_AUTH_REGION`（区划） | `UNE_PAYBOOK`（缴款书）、`UNE_CBILL`（开票）、`FBE_STOCK_OUT`（领票出库） |
| 回答 | "云南省财政厅是哪个区划的执收单位"、"非税收入一般缴款书是什么票种" | "2026 年 1 月云南省开了多少张票、多少钱" |
| 变化频率 | **低**——单位新设/注销、票种新增才变 | **高**——每笔业务都在写 |
| 行数量 | 少——几百到几千行（`FAB_AGEN` 过滤后 336 行） | 多——按月分表（cbill_item 42 张月表） |
| 典型操作 | 查询时被 join、被分组 | 被统计（count/sum） |
| 时间概念 | 本身没有业务发生时间（只有快照/生效期） | 每行都有业务时间（fill_date、pay_date、confirm_date） |

## 2. 变化频率详说

**主数据：一年动几次。** `FAB_AGEN`（单位表）：某协会**新设立** → 插入 1 行；某商会**注销** → 标记/删行；某单位**改名、换行业分类** → 更新那 1 行。除此之外，一年 365 天，这 336 行每天长得一模一样。`FAB_BILL`（票种表）更极端——票种是**省里定的目录**，可能一两年才增减一个：今天 20 行，明年可能还是 20 行。

**交易数据：每笔业务都在写。** `UNE_CBILL`（开票表）：执收单位**每开一张票** → 插入 1 行，一个月几十万次开票 → 一张 `UNE_CBILL_202601` 月表。42 张月表就是这么攒出来的——**不是有人想分表，是单表装不下了**。

同一件事在两边留下的痕迹完全不同：

> **"云南省财政厅"**这个名字，在 `FAB_AGEN` 里只占 1 行，可能三年没变过；
> 但在 `UNE_CBILL` 里，它出现在**几万行**里——每开一张票就被"复印"一次。

一句话总结：**主数据是"字典"，查得多、改得少；交易数据是"账本"，只进不改、越记越厚。**

## 3. 主数据的特征（本系统 5 张表全部命中）

1. **被多方引用**：一个单位会出现在缴款书、开票、领票、库存里——所以适合做 conformed dimension（一致性维度），多个事实 cube join 同一个 `agency`。
2. **每行是一个实体，主键稳定**：`FAB_AGEN.FAGENIDCODE`、`FAB_BILL.FCODE`——事实表通过外键指向它。
3. **带描述性属性**：名称、类型、行业、上级区划——这些就是维度 cube 里的 dimensions，统计时"按单位类型分组"用的就是它们。
4. **可能带快照/版本问题**：`FAB_AGEN` 不加 `FISFINAL='1'` 过滤有 449 行（同码重复），过滤后 336 行——主数据的"最新快照"特性正是 P1 的实测坑（见 01-design.md §10 P1）。

## 4. 为什么主数据 → dims 维度 cube

维度建模（Kimball）的维度表本来就是从主数据来的：**事实表的每个外键，指向一张主数据表，那张表就是维度**。本方案的 5 个维度 cube 就是这么推导出来的——不是先决定"建 5 个维度"再找表，而是先看事实表有哪些外键，每个外键指向的主数据表就是一个维度 cube：

| 事实表外键 | 指向的主数据表 | 维度 cube |
|---|---|---|
| 区划码 | `AFA_AUTH_REGION` | `region` |
| 单位码 | `FAB_AGEN` | `agency` |
| 票种码 | `FAB_BILL` | `bill_type` |
| 项目码 | `FAB_ITEM` | `item` |
| 科目码 | `FAB_SUBJECT` | `subject` |

维度 cube 的价值在于**"被多个事实 cube 复用 join"**——主数据被多方引用（特征 1），所以每个维度 cube 都够格。

**反过来说**，事实表里像 `fstate`、`fbusinesstype`、`FBUSTYPE` 这种字段**不是主数据**——它们是交易行上的状态标记：没有独立实体、主键不稳定、不被别的表引用。所以不建 cube，降级为两条别的路（01-design.md §4/§5）：

- 枚举值少的做成 **case 维度**（如 `agency.type`）
- 需要单独出数的口径做成**每口径单独 measure**（决策 1：pending_count / paid_count / void_count…）

这就是"§4 维度 cube 只有 5 个"的根因：**Oracle 里就只有这 5 张主数据表，其余都是交易表和交易行上的标记字段**——5 不是设计保守，是星型建模的必然结果。

## 5. 变化频率差异对建模的直接约束

| 因为变化频率不同 | 所以（本方案落点） |
|---|---|
| 主数据行少、几乎不变 | 适合做 join 的维度——join 代价小，且不用担心 join 到"旧版本" |
| 交易数据行多、只增不改 | 适合做统计对象——count/sum 越滚越大，所以要按月分表（§6 动态 UNION）+ 预聚合（P6） |
| 主数据会"变"（改名、注销） | `FAB_AGEN` 必须 `FISFINAL='1'` 过滤**最新快照**，否则统计单位数翻倍（P1 实测 449→336） |
| 交易数据**永不改** | P6 回归基线（regress/*.baseline.json）才能 diff 零差异——历史口径是冻结的，今天查和下个月查结果一样 |
