# 16 问数到补建模的闭环流程（单位×项目×科目案例）

> 2026-09-27 实录 + 流程固化。用户问「查询各单位各预算科目下各项目的收入金额及占比情况」，
> 暴露两层问题：① 多口径答案前端展示不全（answer 字段未渲染，占比/次口径不可见）；
> ② 收入日结源表自带预算科目列（FSUB\*）未建模，问数侧只能回答"查不了"。
> 本文档以该案例为线，把「怎么查 → 查不到 → 用户确认 → 补建模」固化为标准闭环：
> ask 负责发现缺口并报告，用户拍板，modeling 负责源表核实与建模变更，回归+复问验收。

## 2. 问数线实录（怎么查、为什么"查不到"）

### 2.1 五步契约的实际执行（cube-ask）

| 步 | 本次实际发生 |
|---|---|
| 1 语义解析 | 「预算科目」映射到 treasury_view.sub_name（treasury ai_context），「项目」映射到 daybook_view.item_name——**两个成员分属两事实表，无联查 view** → 触发歧义处理协议第 2 档（词典无词条 → 反问） |
| 反问 | 输出 ask 三态：`预算科目只在缴库单明细（treasury_view.sub_name）有建模，收费项目只在收入日结（daybook_view.item_name）有建模，两事实表无联查路径…要按哪种口径出收入金额及占比？` 三选项：A 单位×项目（daybook）/ B 单位×预算科目（treasury）/ 两种口径都出 |
| 用户拍板 | 「两种口径都出（各口径独立算占比，不做跨口径合计）」 |
| 2 meta 核验 | 六个成员（daybook 侧 4 + treasury 侧 2）分别过 meta，全部在 |
| 3/4 组装执行 | A：daybook_view 单位×项目×income_amt（82 组）；A′：执收单位口径（75 组）；B：treasury_view 执收单位×sub_name×item_amt（14 组） |
| 5 答案纪律 | 占比分母用不带 dimensions 的全量查询拿（A/A′ 30,200,711.05、B 33,222），Oracle 直查对数一致；qa-log 落盘 |

**agent 侧无过错**：五步契约全部正确执行，"两事实表无联查路径"的判断与模型文件一致。

### 2.2 答案载荷与前端展示缺口（第一层问题）

桥侧契约（chat_server.py CLAUDE_INSTRUCTION 约束 3）：**多口径答案 data 只取主口径的扁平行，
其余口径只在 answer 文本里出 markdown 表**——这是 09-24 为修「嵌套 data 渲染坏」而收紧的
（11 号文档 §6 实测记录）。

前端 `playground-ext/ext-chat.js renderAnswer()` 只渲染 plan → data 表 → assumption → 脚注，
**answer 字段全程未被引用**。后果：

- 占比列：agent 已算好（answer 文本里三张表全带占比），前端不渲染 → 不可见
- B 口径（预算科目）：按契约不进 data，只在 answer 文本 → 整表不可见

> 结论：占比和预算科目"消失"是同一个根因——**契约把次口径塞进了前端不读的字段**。
> 处置（2026-09-27 拍板，并行线不混入建模变更）：**废除主/次口径概念，tables 平等契约**
> ——答案需要几个口径就返回几张表 `tables:[{title,query,rows,total}]`（结构完全对称、
> `data` 字段删除），前端按表渲染、占比列按表级 total 现算（分母由 agent 全量查询提供，
> 前端不算合计）。设计与执行方案＝17 号文档（§7 #4）。

### 2.3 真正的缺口（第二层问题）

用户追问「为什么不能是单位×项目×预算科目一张表」→ 排查源表 → **收入日结表本身自带
FSUBID/FSUBCODE/FSUBNAME 三列，预算科目根本不需要跨事实表**。详见 §3。

## 3. 根因核实：从"查不了"到"能补"

### 3.1 模型现状（排查前）

| 事实/字典 | 科目列 | 项目列 | 备注 |
|---|---|---|---|
| daybook（FNE_INCOME_DAYBOOK，56 源列） | **无**（FSUB\* 未建） | item_code/item_name | 已建 27 成员（4 度量+23 维度），29 列未建 |
| treasury_item（FNE_AGEN_TREASURY_ITEM，12 源列） | sub_code/sub_name | **无**（源表无 FITEMCODE） | "预算科目载体"定位出自此处 |
| FAB_ITEM（项目字典） | 有 FSUBID（未建） | — | |
| FAB_SUBJECT（科目字典） | — | — | yml 注释"项目关联待核实"**有误**（FAB_ITEM 有 FSUBID） |

### 3.2 源表实查（命令与结果，2026-09-27 实测）

```bash
# ① 列存在性：Oracle 数据字典盘点（模型文件只说"建了什么"，这里看"有什么"）
docker exec cube sh -c "node /cube/agent/db.js sql \"SELECT table_name, column_name FROM user_tab_columns WHERE table_name IN ('FNE_INCOME_DAYBOOK','FNE_AGEN_TREASURY_ITEM','FAB_ITEM','FAB_SUBJECT') ORDER BY table_name, column_id\""
#    → FNE_INCOME_DAYBOOK 含 FSUBID/FSUBCODE/FSUBNAME；FNE_AGEN_TREASURY_ITEM 共 12 列，无项目列

# ② 数据质量：空值率 / 组数
docker exec cube sh -c "node /cube/agent/db.js sql \"SELECT COUNT(*) TOTAL_N, SUM(CASE WHEN FSUBCODE IS NULL THEN 1 ELSE 0 END) SUB_NULL, COUNT(DISTINCT FITEMCODE) ITEMS, COUNT(DISTINCT FSUBCODE) SUBS, COUNT(DISTINCT FIMAGENCODE||'|'||FITEMCODE||'|'||FSUBCODE) GRP_3 FROM FNE_INCOME_DAYBOOK WHERE FIODIRECTION='1'\""
#    → 695 行 / SUB_NULL=0（零空值）/ 20 项目 / 15 科目 / 单位×项目×科目 65 组

# ③ 对账：按科目汇总应等于已对数的收入总额
docker exec cube sh -c "node /cube/agent/db.js sql \"SELECT FSUBNAME, SUM(FIMAMT) AMT FROM FNE_INCOME_DAYBOOK WHERE FIODIRECTION='1' GROUP BY FSUBNAME\""
#    → 15 科目合计 = 30,200,711.05，与 Oracle 对过数的收入总额分毫不差

# ④ 层级关系：项目→科目是否严格 N:1（决定"科目"是真下钻层级且无翻倍风险）
docker exec cube sh -c "node /cube/agent/db.js sql \"SELECT FITEMCODE, COUNT(DISTINCT FSUBCODE) N_SUB FROM FNE_INCOME_DAYBOOK WHERE FIODIRECTION='1' GROUP BY FITEMCODE\""
#    → 20 项目全部 N_SUB=1；反向一科目挂多项目（如「中央农网还贷资金收入25」下 3 项目）
```

### 3.3 核实结论

**「单位×预算科目×项目×收入金额×占比」可以在 daybook 一张表内出**：源列存在、零空值、
按科目加总与总额对账一致、项目:科目严格 N:1（科目是项目的上级分组，真下钻层级）。
改法为纯加列维度、不新增 join——按 cube-modeling 动作识别落 **分支②（修改已有 cube）**，
是风险最小的变更类。缴库口径（treasury_item）源表无项目列，"出不了项目维度"仍成立。

### 3.4 为什么当初漏建（四个叠加原因）

1. **建模 scope 需求驱动**：daybook.yml 头注释圈定"收入类别/单位/区划/银行/金额/日期"，
   FSUB\* 不在清单；③-1 核实也是定向 checklist，非全列 profiling
2. **主题锚定**：科目被归属"预算科目载体 = treasury_item"后，无人再问收入侧有无科目冗余列
3. **字典桥接死胡同**：subject.yml"关联待核实"注释把调查停在字典层（且注释本身有误）
4. **无列账本（根因）**：56 列建 27、剩 29 列无声缺席——"没建模"与"没看见"不可区分；
   cube-ask 失败模式 d 的判断依据是 yml 全文，永远看不到"源表有列、yml 没建"

## 4. 两个 skill 的协同：同会话三段式（问 → 建 → 验）

> 2026-09-27 拍板：两个 skill 在**同一会话**先后接力时，交接载体 = 会话上下文本身，
> **不建交接文件**（跨会话交接明确不在本协议范围）。协议只做三件事：
> ① 命名可复用资产（防重做）② 命名必做验证（防漏验）③ 固定切换硬门（防越权）。

### 4.1 分工总表（谁做什么）

| 动作 | cube-ask（只查不改） | cube-modeling（改模型） |
|---|---|---|
| 列 cube/view 已有成员 | 第2步 `cube.js meta`（编译事实，硬 gate）＋第1步模型摘要（桥扫 yml） | 第0步接力检查复用 ask 结论；无接力时查 yml/meta |
| 执行数据库查询 | 第5步高风险对数 `db.js sql`（唯一碰库场景） | ③-1 找原料 `db.js find/cols/dist/matchkey/grain`；三关自检关3 对数 |
| 判断要新增 member | 第2步失败模式 d：**只识别缺口、报三档处置，不建** | 动作识别三问阶梯：决定 ①/②/③，真正加 member 的是 ② |

### 4.2 三段式状态机

```
【问】cube-ask 五步
  │ 语义解析 → meta 核验 → 组装 → query → 答案纪律
  │ 撞缺口（失败模式 d）→ 报缺口 + 三档处置，停
  ▼
  ◆ 切换点 1：用户拍板（"补"/"建"）——ask 的手不许自己升级，唯一入口
  ▼
【建】cube-modeling
  │ 0. 接力检查：本会话 ask 已建立的事实直接用（见 §4.4 免做表）
  │ 1. snap 基线（改前——ask 永远不碰这步）
  │ 2. 原料核实（ask 探查过的复用，没探的补查）
  │ 3. 改 yml / view includes / 词典（yml 本会话已读，直接 Edit）
  │ 4. 编辑后全套验证：check + meta(新成员) + query + 对数 + diff
  │ 5. 基线生长（新组合入 queries.json 重 snap）
  ▼
  ◆ 切换点 2（增量验收，一条查询）：
  │   验收 query = 问阶段主 query ∪ 新增成员（measures/filters/order 不动）
  │   执行一条 → 比对不变量：合计 == 关3 已对数总额；组数符合建阶段预期
  │   通过 → 该结果即原话的验收答案表（可交付，不是废测试）
  ▼
  交付；对不上 → 回【建】修
  词典/ai_context 映射链 → 下次真实提问自然验证（预置零缓存，改完即生效）
```

### 4.3 两道切换硬门

| 门 | 条件 | 防什么 |
|---|---|---|
| 切换点 1（问→建） | **用户拍板**——失败模式 d 的三档处置（查不了/轻扩展/新主题）均需拍板，ask 不许自动升级 | 问数的手改模型（越权） |
| 切换点 2（建→交付） | 编辑后**全套验证全绿**（check/meta 新成员/query/对数/diff）＋ **增量验收不变量对上**（§4.5） | 带病验收、用验收代替回归 |

出口标准是"**增量验收 query 通过、数字对上**"，不是"模型编译过"——本次事故的断点正是
"模型缺列 → agent 答不了"，没有人验证过最后一环。
增量验收的 query 就是原话的答案查询（问阶段主 query ∪ 新增成员，确定性构造，不经重解析），
故"原话能答"由它直接代言；LLM 解析行为留待下次真实提问自然验证。

### 4.4 免做 / 必做表（接力规则，协议核心）

会话里 ask 已建立的 → modeling 直接继承：

| ask 已建立 | modeling 的处理 | 理由 |
|---|---|---|
| 模型 yml 已读（成员清单/口径/命名风格） | **免重读，直接 Edit** | 文件状态在会话内，编辑器本就追踪 |
| meta 核验结论（哪些成员存在） | **免重跑**，动作识别的事实检查凭它定性 ①/② | 编译事实，改前不会变 |
| 口径词典内容、计划表、用户原话 | 直接引用（验收要用原话） | — |
| db 探查结论（源表列/空值/对账，若排查时做过） | 带时间戳采信 | "世界长什么样"是稳定事实 |

modeling 必须**新做**的 → 一个不免：

| 必做 | 为什么不能从 ask 继承 |
|---|---|
| snap 改前基线 | ask 只查不改，从不碰回归——这是第一次有人要动模型 |
| 新成员原料核实（若 ask 没探过源表） | ask 的失败模式 d 只看 yml，看不到源表 |
| 编辑后 check/meta/query/对数/diff | 验证的是"这次改得对不对"，改前的结论全部作废 |
| 词典回写 + 基线生长 | 交付物，ask 无此动作 |
| 增量验收（一条 query ＋ 不变量） | 闭环出口，改完 ≠ 能答；重走五步 4/5 与建模三关重复（meta/组装/执行/对数都已做过） |

**一句话版**：ask 攒下的"世界事实"全部继承；modeling 的"变更验证"一个不免。

### 4.5 各段步骤明细

**【问】cube-ask 五步**（本次案例实录见 §2.1）：

1. 桥注入预置上下文（模型摘要＋通道＋词典，每问现扫 yml，零缓存；Claude Code 直跑时第1步自读 yml）
2. 语义解析 → 计划表（成员只来自 ai_context/词典，不发明）
3. `cube.js meta` 成员核验（硬 gate）
4. `cube.js query` 执行（语义层，非裸 SQL）
5. 答案纪律：占比只基于返回行、分母用不带 dimensions 的全量查询；涉金额 `db.js sql` 对数
6. 撞缺口 → 报"查不了"＋缺口＋三档处置，**停**

**【建】cube-modeling**（含第 0 步接力）：

1. 公共前置：`cube.js check`（编译）＋ `db.js count`（连通有数据）
2. **第 0 步接力检查**：本会话刚执行过 cube-ask → 按 §4.4 免做表继承，动作识别
   的事实检查凭 ask 的 meta 结论定性；无接力（纯建模需求）→ 照常自查
3. 动作识别三问（成员已存在只缺交付？→①；原料已承载缺成员？→②；原料全新？→③）
   ——本次落 ②；**识别为 ② 后动 yml 之前立即 snap 基线**
4. ②流程：（读 yml——已接力则跳）→ snap → `db.js` 核实新成员原料（§3.2 即本步产物）→
   加成员（description/ai_context 必写，view 侧 ai_context 镜像同步）→
   三关自检（编译/查询跑通/Oracle 对数）→ **diff 回归**
5. 复合序列：② 加成员 → 追加 ① 交付面 view includes 补成员（只增不删）→ 再 check/query/diff
6. 词典回写 ＋ 基线生长（§5 步骤 3/5）

**【验】增量验收（一条查询，非重走五步；2026-09-27 拍板）**：

> 重走五步与建模三关 4/5 重复（meta 核验/组装/执行/对数都做过），验收唯一增量是
> "原话的答案查询能不能出"——把它确定性构造出来跑一条即可。

- **构造**：验收 query = 问阶段主 query ∪ 新增成员——dimensions += sub_name（本例），
  measures/filters/order 不动；新增度量同理走 measures ∪。多口径时只扩展"因缺口缺维度"
  的那条（本例 A/A′ 加 sub_name；B 缴库口径维持原样——缺的是源表列，不是建模），
  验收后原话答案收敛为单表，两口径拆分 workaround 自然作废
- **执行一条**，比对两个不变量：
  ① 合计 == 关3 已对数总额（同表同度量同过滤，分组细化不改总和——Oracle 都不用再碰）
  ② 组数符合建阶段 db 探查预期（本例收入方向 单位×项目×科目 65 组，全表含支出行略多；
  组数逼近 limit 则抬 limit 重跑一次）
- **产出即交付**：这条查询的结果就是原话的验收答案表
- **刻意不验**：原话 → 词典 → 新成员的 LLM 解析行为——会话内自审置信度增量 ≈ 零，
  交由下次真实提问自然验证（预置上下文零缓存现扫 yml，modeling 改完即生效）；
  高风险变更（动 join/口径语义、数字对外汇报）可加测 T2：python urllib POST :4100
  真问一次（curl 中文 body 踩 GBK 坑，用 python）
- 对不上 → 回【建】修，不带病交付

## 5. 补建模标准流程（六步 checklist，本文档固化）

每次「加维度 → 交付面补成员 → 回归验证 → 交付」照此打勾：

| # | 步骤 | 动作 | 不过的后果 |
|---|---|---|---|
| 1 | 改前拍快照 | `cube.js snap regress/<cube>.baseline.json -f regress/<cube>.queries.json`（**必须先于动 yml**） | 改完才拍 = 存照里已是坏数字，diff 永远绿，等于没验 |
| 2 | 核实原料 | `db.js`：列存在（user_tab_columns）→ 空值率 → 对总账 → 与既有成员层级关系 | 拍脑袋加列 = 脏数据进交付面 |
| 3 | 改模型（三处口径同步） | cube 加成员（description/ai_context）＋ view includes ＋ **口径词典词条**——三处不一致 = 下次问数仍映射旧口径 | |
| 4 | diff 回归 | `cube.js diff <baseline> -f <queries>`：老查询答案一个都不能变（退出码 1 必须修复） | 编译过 ≠ 数字对，diff 是存量口径唯一抓手 |
| 5 | 基线生长 | 把新维度组合追加进 `queries.json` 并重新 snap | 该组合脱离回归保护，下次变更 diff 不到它 |
| 6 | 增量验收 | 问阶段主 query ∪ 新增成员，执行一条；比对合计不变量（== 关3 对数总额）＋组数预期；结果即答案表（§4.5） | "模型改好了但 agent 仍答不了"——本次事故正是断在此环；全量复问 4/5 是重复执行 |

两条验证线的分工（勿混）：
